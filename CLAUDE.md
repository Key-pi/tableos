## Что это за проект

- **Botera** — сеть продуктов владельца. Этот репозиторий — **Botera Shop**:
  Telegram-бот и Django Admin одного бизнеса (заведение или магазин),
  multi-tenant (много партнёров в одной базе, у каждого свой бот).
- **Botera Master** (мастера) — отдельный проект, уже в разработке.
  **Partnership** и **Discovery** — будущие отдельные сервисы. Никаких
  импортов их моделей и общих таблиц; связь только через API/события с
  `event_id`, и они никогда не обязательны для заказа или оплаты.
  Подробно: `docs/product/ECOSYSTEM_DIRECTION.md`.
- Имя «TableOS» уходит из всего, что видят люди. Внутренние имена в коде и
  базе (`tableos` в `pyproject.toml`, пакеты, таблицы) не трогаем.
- **Стол — один из каналов заказа**, не основа: `Order.channel` = `table` /
  `pickup` / `delivery` / `shipping` (отправка почтой). Способ заказа гость
  выбирает сначала (кнопка или QR стола), он хранится в `Cart.channel`; у
  позиций меню отметки, в каких способах они продаются.
- **ADR-0009:** одна модель заказа/счёта/оплаты для всех каналов; никаких
  «ЗаказДоставки»/«СчётДоставки». Данные канала — поля заказа
  (`requested_for`, `delivery_*`, `shipping_*`), поведение — модуль на
  семейство: стол —
  `apps/tables` + `apps/billing/table_bills.py`; удалённые каналы —
  `apps/billing/remote_orders.py` (`REMOTE_CHANNELS`,
  `Order.REMOTE_CHANNELS`) и бот `bot/handlers/remote_checkout.py`. Ядро
  счёта `apps/billing/services.py` про каналы не знает. Различать каналы по
  `order.channel`, а не по `order.table_id`.

## Решения владельца, которые легко нарушить

- **Визиты (PQ-026, ADR-0007):** счёт, кнопка «Запросить счёт» и
  «стол рассчитан» считаются по визиту стола, не по истории стола.
- **Автозакрытие (PQ-027):** закрываются только полностью оплаченные сессии;
  шаг автозакрытия никогда не откатывает оплату.
- **Счета (PQ-028):** менять/аннулировать может владелец или сотрудник с
  правом от владельца; всё в `BillAdjustment`; итог не ниже оплаченного;
  счёт с бонусами только аннулируется (бонусы возвращаются `reversal`).
- **Гость подтверждает получение (PQ-029)** из любого нефинального статуса.
- **Кешбэк (PQ-030):** база `full_total` или `money_paid` на программу.
- **Источники переходов (PQ-031):** гость закрепляется за первым источником,
  все переходы пишутся; источники создаёт владелец в Admin; цифры — только
  переходы и новые гости, только в Admin.
- **Доставка сообщений (ADR-0008):** рассылки — не больше одного раза на
  гостя (`BroadcastDelivery`); рабочие уведомления — хотя бы один раз.
- **Модули — конструктор (PQ-033):** каждый модуль включается отдельно,
  настраивается своими полями и не меняет поведение других (любой набор,
  в том числе один модуль). Владелец включает варианты, гость выбирает из
  включённых; не зашивать один вариант в канал. Оплата удалённых заказов —
  «переводом заранее» и/или «при получении» на модуль
  (`Order.payment_timing`). Новый модуль — с тестом, что он работает один
  и что его настройки и выключение не задевают остальные
  (`tests/apps/billing/test_shipping.py:ModuleIndependenceTests`).
- **Самовывоз:** перевод на реквизиты заведения (подтверждает
  владелец/менеджер/кассир) и/или оплата на месте, бонусы по желанию,
  телефон обязателен, только в часы работы (`OpeningHours`).
- **Доставка (PQ-032):** то же, что самовывоз, плюс адрес (текст
  обязателен, геолокация по желанию, последний запоминается); цена —
  фикс, бесплатно от суммы, минимальный заказ; цена — строка заказа
  `OrderItem.kind = delivery_fee` без позиции меню; персонал отмечает
  «в пути» и «доставлено».
- **Отправка почтой (PQ-034):** службы без API (Нова Пошта, Укрпошта,
  Meest — какие включил владелец), отделение или почтомат текстом, последний
  получатель запоминается; пересылка — по тарифу перевозчика и/или фикс в
  заказе (строка `delivery_fee` «Пересылка»), гость выбирает; оплата —
  перевод и/или наложенный платёж (`Payment.Method.COD`); без ТТН заказ не
  «отправлен» (`mark_order_shipped`); «Получен» — гость или персонал; без
  часов работы.
- **Права владельца (PQ-035):** реквизиты для перевода — только владелец
  (`owner_only_fields`), при смене владельцу сообщение «Безопасность»;
  записи владельца меняет только владелец; не-владелец не выдаёт прав выше
  своих.
- **Неоплаченные заказы (PQ-036):** лимит открытых неоплаченных удалённых
  заказов на гостя (`remote_unpaid_orders_limit`, 2) и автоотмена
  неподтверждённого перевода (`transfer_wait_minutes`, 60; beat
  `billing.cancel_expired_transfer_orders`).
- **Возвраты (PQ-037):** полный и частичный по строкам оплаченного счёта
  (`refund_bill_lines`), отдельная запись `Refund`, оплата не правится;
  бонусы за возвращённое — гостю, кешбэк — снять (не ниже баланса); право
  как на изменение счёта; деньги вручную, гостю сообщение.
- **Конструктор, часы и уведомления (PQ-038):** свои часы у самовывоза и
  доставки (`OpeningHours.scope`, без своих — общие); сотрудник выбирает
  способы заказа для уведомлений (`notify_channel_*`). Реквизиты общие.
- **Языки (PQ-040):** по умолчанию украинский; готовые тексты uk/ru/en;
  владелец выбирает основной и включённые языки гостей и может заменить любой
  текст гостя на каждом языке (`BotText`); гость — язык Telegram или выбор в
  профиле; персонал и Admin — свой язык (`User.language`, переключатель в
  шапке Admin), по умолчанию — язык платформы `uk`. Уведомления — на языке
  получателя (`speaking_to_employee` / `speaking_to_guest`). Документация —
  русская.
- **Запуск ботов (PQ-041, PQ-042):** неисправный бот не мешает остальным,
  его причина — в `BotInstance.runtime_state` (Admin → Боты); список
  перечитывается раз в минуту без перезапуска; «Unauthorized» останавливает
  только этот бот до смены токена. `bot/main.py:run_polling` — только для
  эмулятора и нагрузочного теста.
- **Подключение бизнеса (PQ-045):** регистрация — в будущем общем боте
  платформы («Hub», отдельный сервис для Shop и Master, туда же ошибки
  PQ-039); бизнес работает сразу, владельцу платформы сообщение; пока
  бесплатно. В Shop — только части для любого входа.
- **Приглашения сотрудников (PQ-046):** ссылку `start=inv_…` выдают владелец
  и менеджер (роль не выше своей, не владелец), одноразовая, 24 часа;
  подтверждает выдавший или владелец; доступ к Admin не даёт
  (`apps/employees/invites.py`).
- **Сети заведений (PQ-047, `docs/architecture/NETWORKS.md`):** «Сеть» над
  заведениями, точка остаётся партнёром (граница данных не меняется). Один
  вход владельца с переключателем точки, менеджер на несколько точек
  (`extra_partners`), отчёт по сети. Действия за точку — `acts_for_partner`
  / `owns_partner`, не `user.partner_id`. Один бот на сеть (`Network.bot`,
  выбирает владелец в карточке сети): точку обновления выбирает
  middleware, обработчики не знают о сети; бот для точки —
  `bot_for_partner`. Общие бонусы (`Network.bonus_mode`): журнал у точки,
  баланс — сумма по сети, замок `NetworkWallet`; баланс показывать через
  `bonus_balance(guest)`, код гостя искать через
  `find_guest_by_customer_code`. Владелец и менеджеры сети в боте других
  точек — копии их профиля сотрудника (`EmployeeProfile.mirrored_from`,
  `apps/employees/network_staff.py`): копии не править и не удалять руками,
  их держит в порядке `sync_network_staff` (сигналы).
- **Mini App (PQ-048, `docs/architecture/MINI_APP.md`):** адаптер `webapp/`
  рядом с ботом, модуль `module_webapp_enabled` включает владелец, бот не
  меняется; рабочий экран персонала — свой модуль
  `module_staff_screen_enabled` (без гостевого Mini App и корзины). Каждый запрос — с `initData`, подпись проверяется токеном этого
  бота; партнёр — от бота и выбора гостя; действия — только через сервисы,
  как в боте. Порядок: гость → персонал → экран бара (общий планшет — без
  Telegram, привязка к точке ссылкой из Admin). Фото позиций — загрузка в Admin.
  Экран кухни и бара — экран приготовления, отдельный модуль
  (`module_kitchen_screen_enabled`, нужен только модуль заказов): ссылка
  экрана из Admin видна один раз (хранится хеш), на экране только принятые
  заказы и без данных гостя; бар и кухня — по `MenuCategory.station`, заказ
  «Готов», когда свою часть отметили все экраны (`apps/orders/kitchen.py`);
  место без работающего экрана — как «не указано».
- **Каталог (PQ-049, `docs/architecture/CATALOG.md`):** расширяется в ветке
  `catalog` по шагам (витрина → варианты и добавки → остатки → переводы и
  импорт), владелец проверяет каждый. Подкатегории — два уровня; расписание
  категории — вне времени видна, но не продаётся (проверка на сервере
  `first_not_on_sale`, быструю продажу не ограничивает); метки — готовые +
  свои; витрина — модуль `module_showcase_enabled`. Варианты и добавки —
  модуль `module_options_enabled`: варианты — один список со своей ценой,
  добавки — общие группы на позициях или категориях, вес — фасовками, быстрая
  продажа — с выбором; что выбрано и сколько стоит — только
  `apps/menu/options.py:resolve_choice`; выбор — в имени и цене строки заказа,
  при оформлении проверяется заново. Остатки — модуль `module_stock_enabled`
  (позиции с `track_stock`): заказ списывает при оформлении, отмена
  возвращает; гость видит «нет в наличии» / «осталось мало», без числа;
  быстрая продажа списывает, может уйти ниже нуля; возврат кладёт на склад
  только с отметкой персонала; всё — через `apps/menu/stock.py` с записью
  `StockMovement`, Admin пишет остаток только пересчётом (`count_stock`).
  Переводы каталога: языки — те же uk/ru/en; владелец переводит в Admin
  (`translations` у моделей каталога, поля — для включённых языков гостей,
  кроме основного); гость видит перевод (`translated`), без перевода —
  оригинал; строка заказа хранит имя на основном языке для персонала, экраны
  гостя строят его заново (`line_names_in`, без запросов); импорт отложен.
- **Данные гостей (PQ-024):** хранятся, гость меняет сам. Мониторинг ошибок —
  будущий Telegram-бот для всех систем Botera (PQ-039), пока не делаем.
- Новый продуктовый смысл без решения владельца не выбирать — спросить.

## Порядок блокировок (не менять без причины)

- Оплата: `Bill → Order → GuestProfile → BillingRequest → TableSession → TableVisit`.
- Активация стола: `GuestProfile → Table → свои TableSession → TableVisit`
  (стол — `select_for_update(no_key=True)`, AA-040).
- Строку-«родителя», которую блокируют только для очереди (её ключ не
  меняется), блокировать `no_key=True`: `FOR UPDATE` не пускает проверку
  внешних ключей других транзакций при `COMMIT` и даёт deadlock.
- Изменение счёта и возврат: `Bill → BillItem → GuestProfile → Order`.
- Вызов персонала «Иду»: только `GuestCall` (`take_guest_call`).
- Приглашение сотрудника: `StaffInvite → EmployeeProfile`.
- Экран кухни и бара «Готово»: только `Order` (до чтения `OrderStationReady`).
- Бонусы при общем балансе сети: `GuestProfile` (точки) → `NetworkWallet`.
- Остатки: строки `MenuItem`/`MenuItemVariant` — последними в транзакции,
  сначала позиции, затем варианты, каждые по id, `no_key=True`
  (`apps/menu/stock.py:_lock`).
- На PostgreSQL `select_for_update` с nullable-join только с `of=("self",)`.

## Как работаем

- Ветка: `clean-project-rules`. Коммитить небольшими зелёными шагами;
  пушить в неё, когда владелец просит.
- Тесты — только в `tests/` по модулям кода (`tests/apps/<приложение>/`,
  `tests/bot/`, `tests/core/`, `tests/webapp/`), файлы `test_*.py`; запуск
  части — `manage.py test tests.apps.billing` (`docs/engineering/TESTING.md`).
- Сначала тест, который падает; для блокировок — тест на PostgreSQL
  (`TransactionTestCase`, `skipUnless(connection.vendor == "postgresql")`) и
  проверка мутацией (убрать защиту → тест падает).
- Полный прогон на SQLite **и** PostgreSQL 16 перед каждым коммитом с
  изменением поведения; миграции — вперёд/назад/вперёд на PostgreSQL.
- Ruff: не добавлять новых нарушений в изменённых файлах (сравнивать с
  `git stash`); старые не чинить заодно.
- Документы обновлять в том же коммите: `AS_IS_ARCHITECTURE.md`,
  `FEATURE_MATRIX.md`, PQ/ADR при решении, строка прогона в `TESTING.md`.
  Число тестов также упоминается в `AGENTS.md`, `.agents/skills/…/SKILL.md`,
  `PROJECT_CHEATSHEET.md`, AS-IS — менять везде.
- Документация — по-русски. Тексты для людей (бот, Admin) пишутся в коде
  по-русски внутри `_()` из `core/i18n.py` (значения — параметрами:
  `_("Сумма: {total} грн", total=...)`), переводы на украинский и английский —
  в `locale/{uk,en}/LC_MESSAGES/django.po`: `python
  infrastructure/scripts/messages.py update`, перевести, `… compile`
  (PQ-040, `docs/architecture/LANGUAGES.md`; `tests/core/test_i18n_catalog.py`
  проверяет полноту). Подписи, вычисляемые при импорте (`verbose_name`,
  `choices`, `@admin.display`, `fieldsets`), — `gettext_lazy as _lazy`; в
  шаблонах — `{% load botera_i18n %}{% tr "…" %}`; текст для другого
  человека (уведомление) — внутри `speaking_to_employee(...)` /
  `speaking_to_guest(...)`; `_` не использовать как переменную
  (`_unused`). Сообщения бота в HTML, все динамические значения через
  `escape_html`. У новых полей и вариантов — `verbose_name` и подписи
  по-русски (`tests/core/test_admin_language.py`); строки темы Admin —
  `locale/<язык>/LC_MESSAGES/theme.po`.
- Telegram callback_data ≤ 64 байт: UUID в виде hex, состояние шагов — в
  самом callback (без FSM, где можно).

## Команды

```bash
# тесты, SQLite (нужен .env с BOT_TOKEN_ENCRYPTION_KEY — ключ Fernet)
python3 manage.py test --noinput

# тесты, PostgreSQL 16
DJANGO_USE_SQLITE=false POSTGRES_HOST=127.0.0.1 python3 manage.py test --noinput

python3 manage.py makemigrations --check --dry-run
ruff check --no-cache <изменённые файлы> --output-format concise
docker compose config --quiet

# продакшен: docs/engineering/DEPLOYMENT.md (docker-compose.prod.yml,
# core.settings.production, зависимости — requirements.lock через pip-compile)

# весь стек в Docker (пошагово: docs/engineering/DEVELOPMENT.md)
cp .env.example .env && docker compose up --build
docker compose logs init        # логины и ссылки на столы демо-данных
```

Подводные камни окружения: таймзона по умолчанию `Europe/Kyiv` (старое
`Europe/Kiev` в `.env` читается как Kyiv, но локальный PostgreSQL с
`timezone = 'Europe/Kiev'` в `postgresql.conf` не стартует); Celery в тестах
eager; `docker compose up` поднимает db, redis, разовый init (миграции +
`seed_baseline_demo --keep-existing`), затем web, worker, beat, bot
(`runbot --wait`) — beat и сервис bot ровно по одному (процессы бота —
`--processes`/`BOT_PROCESSES` внутри сервиса). Демо-данные берут токены
ботов и Telegram ID владельца из `.env` (`DEMO_*`).
