# Botera Shop — тесты и проверка

## Команды базовой проверки

На аудите в виртуальном окружении репозитория выполнялись (без `.venv` —
то же через `python3`, как в `CLAUDE.md`; SQLite включается
`DJANGO_USE_SQLITE=true`, PostgreSQL — `DJANGO_USE_SQLITE=false
POSTGRES_HOST=127.0.0.1`):

```bash
env DJANGO_USE_SQLITE=true PYTHONDONTWRITEBYTECODE=1 ./.venv/bin/python manage.py check
env DJANGO_USE_SQLITE=true PYTHONDONTWRITEBYTECODE=1 ./.venv/bin/python manage.py makemigrations --check --dry-run
env DJANGO_USE_SQLITE=true PYTHONDONTWRITEBYTECODE=1 ./.venv/bin/python manage.py test
./.venv/bin/ruff check --no-cache .
./.venv/bin/ruff format --check --no-cache .
docker compose config --quiet
python3 infrastructure/scripts/check_docs.py   # документация против кода
```

**Документация против кода** (с 2026-11-14, решение владельца — чтобы не
нужны были регулярные аудиты): `tests/core/test_docs.py` в каждом полном
прогоне проверяет ссылки `path` / `path:symbol` в живых документах (кроме
датированных `docs/audits/` и `docs/legacy/`),
ссылки и якоря Markdown во всех документах, что каждая модель названа в
AS-IS, каждая задача Celery и запись beat — в `BACKGROUND_JOBS.md`, каждая
команда `manage.py` — в документах, каждый `module_*_enabled` — в таблице
«Модули заведения», каждый обработчик бота — в `BOT_RUNTIME.md`, каждая
переменная `core/settings/env.py` — в примерах `.env` или руководствах; форму
инструкций (`CLAUDE.md` до 200 строк, у правил `.claude/rules/` есть `paths:`,
совпадающие с файлами); пять ячеек в строках PQ; последний ADR в `AGENTS.md`;
одно число тестов в шапке, в последней строке журнала с числом и в AS-IS.
Сообщение называет документ и строку. Тот же отчёт без запуска тестов —
`infrastructure/scripts/check_docs.py`.

На базовой проверке 2026-07-27 прошли `check`, проверка миграций, тесты и
конфигурация compose; тестов было **139**. На 2026-11-14 тестов **1216**;
они проходят на SQLite (29 пропущено — тесты только для PostgreSQL) и на
PostgreSQL 16. Каждый полный прогон записывайте в таблицу в конце документа.

**Требования к окружению.** Тесты шифруют токены ботов, поэтому
`BOT_TOKEN_ENCRYPTION_KEY` должен быть корректным ключом Fernet — положите
его в `.env` (см. `DEVELOPMENT.md`); без него около 60 тестов падают с
`BOT_TOKEN_ENCRYPTION_KEY must be configured`. С B5 таймзона по умолчанию —
`Europe/Kyiv`, а старое `DJANGO_TIMEZONE=Europe/Kiev` читается как
`Europe/Kyiv` (AA-034). Локальный PostgreSQL, созданный `initdb` в такой
системе, сам может иметь `timezone = 'Europe/Kiev'` в `postgresql.conf` и
перестать запускаться, когда старого имени не станет; замените на
`Europe/Kyiv`. Ruff на базовой проверке показал **21 старое нарушение** и
**54 файла, которые переформатировал бы**. На 2026-11-14 (`ruff 0.16.9` в
окружении разработки; `pyproject.toml` для dev просит `ruff>=0.13,<0.14`)
`ruff check --no-cache .` — **13 старых замечаний** (11 E501 в
`bot/handlers/staff.py`, `bot/handlers/profile.py` и тестах, 1 F401, 1 UP012),
`ruff format --check` — 294 файла: форматирование всего репозитория не
применяется. Правило — не добавлять новых замечаний в изменённых файлах
(«до» и «после» — одной версией Ruff, без `git stash`; команды — в навыке `.claude/skills/tableos-development/SKILL.md`). Не утверждайте, что Ruff «зелёный», пока это не
изменится и не будет перепроверено. Полный вывод и
версии инструментов — в [`../audits/BASELINE.md`](../audits/BASELINE.md).

## GitHub Actions

С 2026-11-14 на каждый пуш в любую ветку и на каждый pull request GitHub сам
запускает `.github/workflows/tests.yml`: два задания параллельно — SQLite и
PostgreSQL 16 (с Redis 7), в каждом `manage.py check`,
`makemigrations --check --dry-run`, `infrastructure/scripts/check_docs.py` и
весь набор тестов. Python 3.12 — как в образе Docker. Ключ шифрования токенов
создаётся заново на каждый запуск и нигде не хранится; секретов у задания нет.
Новый пуш в ту же ветку отменяет ещё идущую проверку. Репозиторий публичный —
минуты GitHub Actions для него бесплатны.

Как смотреть результат:

1. На странице репозитория на GitHub — вкладка **Actions**: список запусков,
   у каждого ветка и коммит.
2. У коммита (в списке коммитов ветки) — значок: жёлтая точка — идёт,
   зелёная галочка — всё прошло, красный крестик — что-то упало.
3. Красный — открыть запуск, задание (SQLite или PostgreSQL 16) и упавший шаг:
   там вывод теста. Перезапустить без нового пуша — кнопка **Re-run jobs**.
4. Из терминала: `gh run list --branch <ветка>`; без `gh` — открытый API
   `https://api.github.com/repos/Key-pi/tableos/actions/runs?branch=<ветка>`.

Ruff в CI не запускается (13 старых замечаний, AA-053). CI не заменяет полные
прогоны перед коммитом с изменением поведения — он ловит то, что забыли
прогнать, и проверяет чистую копию репозитория без `.env`.

## Где лежат тесты

Все тесты — в папке `tests/` в корне, разложены по тем же модулям, что и код
(с 2026-11-06, по просьбе владельца; в модулях остаётся только код):

```
tests/apps/<приложение>/test_*.py   # apps/<приложение>/...
tests/bot/test_*.py                 # bot/...
tests/core/test_*.py                # core/...
tests/webapp/test_*.py              # webapp/...
```

- Новый тест — файл `test_<тема>.py` в папке своего модуля под `tests/`; в
  каждой папке есть `__init__.py` (без него `manage.py test` папку не
  найдёт).
- Общие заготовки других тестов импортируются как модули тестов:
  `from tests.webapp.test_guest_api import make_venue`.
- Запуск части: `python3 manage.py test tests.apps.billing`,
  `python3 manage.py test tests.webapp.test_kitchen.SplitScreensTests`.
  Метка вида `apps.billing` после переноса тестов не находит.
- Исключение — `core/test_runner.py`: это не тест, а запускатель тестов из
  настроек (`TEST_RUNNER`), он остаётся в `core`.

## Какие тесты нужны для какого изменения

| Изменение | Минимальная проверка |
|---|---|
| Модель/миграция | `makemigrations --check`, точечные тесты, тест данных/миграции; PostgreSQL, если важны ограничения или блокировки |
| Партнёры/права | тесты сервиса с двумя партнёрами + запросы/формы бота и Admin |
| Состояние заказа/сессии | тесты переходов и повторного callback; конкурентный тест на PostgreSQL |
| Счета/бонусы/деньги | фикстура со сверкой журнала, граничные и отрицательные случаи, конкурентный тест распределения/баланса на PostgreSQL |
| Admin | тесты формы изменения, действий, inline, фильтров списка; проверка побочных эффектов сервиса |
| Маршрутизация/тексты бота | порядок роутеров/фильтров, устаревший callback, изменённая подпись кнопки/схема callback |
| Celery/уведомления | постановка после коммита, повтор, дублирующий воркер, падение, регистрация задач |
| Чистка/перенос | поиск импортов и API, проверка динамических регистраций, характеризующие тесты, `git diff --check` |

оплата бонусами, финальная оплата, аннулирование против оплаты, отмена

приглашения), `tests/apps/bonuses/test_shared_bonuses.py` (две точки тратят
один баланс сети, повтор быстрой продажи), `tests/apps/menu/test_stock.py`
(последний товар), `tests/webapp/test_kitchen.py` (два экрана отмечают
«Готово»), `tests/apps/analytics/test_system_load.py` (снимок PostgreSQL),
`tests/apps/tables/test_floor_plan.py` (два человека расставляют один зал),

стол), `tests/apps/tables/test_reservations.py` (две брони одного стола).
SQLite к тому же игнорирует `select_for_update`,
поэтому блокировка, которую PostgreSQL отвергает (AA-033), там не видна:
**перед закрытием любого батча, который трогает блокировки, ограничения или
запросы с `select_for_update`, прогоните весь набор на PostgreSQL.**

```bash
docker compose up -d db
env DJANGO_USE_SQLITE=false POSTGRES_HOST=localhost PYTHONDONTWRITEBYTECODE=1 \
  ./.venv/bin/python manage.py test
```

Пользователь базы из compose владеет базой и может создать тестовую.
Так же прогоните весь набор перед выкаткой миграций B2–B5 в продакшен.

## Порядок проверки конкурентности

SQLite не доказывает работу построчных блокировок PostgreSQL, частичных
уникальных ограничений и параллельных транзакций. Конкурентный тест должен
использовать отдельные соединения/транзакции, синхронизировать
конкурирующие операции (`threading.Barrier`) и проверять итоговое
сохранённое состояние, а не только то, что вызовы не упали. Затем —
проверка мутацией: убрать защиту и убедиться, что тест падает.

## Безопасность тестовых данных

- Фикстуры партнёров держать раздельными, проверки «между партнёрами» —
  явными.
- Не использовать продакшен-токены ботов и данные пользователей.
- Денежные значения — детерминированные; проверять журнал, баланс и отчёт.
- Характеризующие тесты фиксируют исходное поведение; если тест закрепляет
  известный дефект до утверждённого батча, это помечается в тесте.

## Готовность исправления поведения

1. Тест показывает прежний дефект или неподдержанный путь.
2. Исправление в сервисе-владельце сохраняет разрешённое текущее поведение.
3. Адаптеры (бот, Admin, задачи) не могут его обойти.
4. Последствия для миграций, данных и отката описаны.
5. Прогнаны нужный набор тестов и описанные базовые проверки; старые
   несвязанные замечания линтера указаны отдельно, а не скрыты.
