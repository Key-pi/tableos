# ADR-0003: Деньги и жизненный цикл меняются только через защищённые команды

**Статус:** принято
**Дата:** 2026-07-27

## Контекст

Аудит обнаружил несколько независимых путей изменения критичных данных: стандартные формы Django Admin позволяют менять `Order`, `Bill`, `BillingRequest`, `TableSession`, кампании и записи, похожие на журнал; действие для `BillingRequest` использует `.update()` выборки и допускает обратные переходы. При этом доменные сервисы содержат часть нужных проверок. Есть подтверждённые риски конкуренции: смена статуса устаревшего `Order` без перезагрузки под блокировкой, две активные сессии у гостя и одна `OrderItem` в двух распределениях по счетам. Повторное списание бонусов может не сериализоваться на балансе гостя.

## Решение

Для финансовых сущностей и сущностей с жизненным циклом установить единую границу команд:

* разрешённый переход состояния определяется явно и выполняется сервисом или политикой владельца;
* команда получает текущие строки через `select_for_update()` в стабильном порядке и фиксирует ключ идемпотентности или корреляции, если вызов повторяемый;
* финансовый журнал только дописывается, изменение баланса — часть той же защищённой команды;
* у распределения позиции счёта один активный владелец, защищённый блокировкой и стратегией на уровне базы после миграции данных;
* Django Admin показывает финальные поля и поля жизненного цикла только для чтения; разрешённые операции выполняются явно названными действиями, вызывающими ту же команду, с исполнителем и причиной;
* прямой `save` модели, правка inline и `.update()` выборки — недопустимые обходы.

## Последствия

Положительные:

* уведомления, история и итоги не расходятся между ботом и Admin;
* повтор callback или задачи не создаёт нового экономического эффекта;
* след аудита можно сопоставить с исполнителем и причиной.

Ограничения:

* интерфейс Admin становится менее свободным и потребует специальных действий и форм;
* конкуренцию за блокировки и хранение идемпотентности нужно измерять и покрывать тестами;
* существующие модели не меняются все сразу: нужны небольшие батчи миграций с откатом.

## Область и проверка

Первыми покрываются статус заказа, запрос счёта, распределение по счёту и оплата, списание бонусов и сессия стола. Для каждого сценария нужны тесты: неразрешённый переход, двойная отправка, параллельный запрос в PostgreSQL, невозможность обхода через Admin и корректный откат при ошибке. Изменение считается завершённым, только если публичный путь бота и Admin вызывает одну команду и инвариант базы и данных проверен.

## Что сделано в B2 — 2026-08-06

B2 устанавливает конкретные границы жизненного цикла, не меняя публичные
имена команд:

* `transition_order_status()` перезагружает канонический `Order` под
  `select_for_update()` до проверки перехода, записи истории и постановки
  уведомлений после коммита. Повторный callback отклоняется по текущему
  состоянию, а не применяется к устаревшему объекту.
* Активация сессии стола блокирует в порядке `GuestProfile → Table → активные
  строки TableSession`. Блокировка гостя сериализует два скана QR разных
  столов; новое частичное уникальное ограничение
  `unique_active_table_session_per_partner_guest` — долговечная защита, а
  прежнее поведение «побеждает последний скан» сохраняется закрытием
  предыдущей активной сессии до создания новой.
* Закрытие сессии, выставление и оплата счёта и переходы запросов счёта
  перезагружают и блокируют свою каноническую строку до проверки состояния.
  Завершение оплаты идёт `Bill → Order → BillingRequest → TableSession`;
  уведомления и эффекты Telegram остаются после коммита или в задачах.
* Формы Admin заказа, корзины, счёта, распределения и сессии показывают поля
  жизненного цикла, связей и производные только для чтения. Утверждённые
  операции состояния — явные действия, вызывающие сервис заказа, счёта или
  сессии стола; `BillingRequestAdmin` больше не использует `.update()`
  выборки.

До создания ограничения сессии локальный аудит данных SQLite нашёл 2 активные
сессии и 0 дублей активных пар `(partner, guest)`. Выкатка в продакшен должна
выполнить тот же запрос дублей до применения миграции; этот батч данные не
исправляет. Тесты конкурентности только для PostgreSQL включены, но не могли
запуститься в локальном окружении, потому что не было PostgreSQL/Docker.

## Уточнение пути оплаты в B3 — 2026-08-06

Команда оплаты бонусами — одно намерение персонала и сервиса, а не отдельный
процесс Admin «списать, затем рассчитать счёт с нулевым итогом»:

* `pay_bill_with_bonuses()` блокирует `Bill → Order → GuestProfile`, проверяет
  баланс журнала в пределах партнёра и применяет максимальную сумму,
  разрешённую активной программой партнёра, по курсу 1 бонус = 1 грн.
* Если бонусы не покрывают счёт, команда сохраняет списание и оставляет
  денежный остаток в счёте. Оплата остатка наличными или терминалом даёт
  смешанный способ оплаты заказа.
* Если бонусы покрывают счёт полностью, та же команда создаёт обычную запись
  `Payment.Method.BONUSES` на номинал бонусов и закрывает счёт;
  `Bill.paid_amount` по-прежнему означает только деньги. Действия Admin
  `settle_zero_total_bonus_bills` нет, и Admin не может создавать бонусные
  оплаты напрямую.
* Расчёт по оплате — текущее базовое соответствие для наград за заказ;
  существующее значение `ORDER_COMPLETED` — имя для совместимости, а
  расширение событий под партнёра — будущая работа с программами.

## Исправление после B3 — 2026-10-23

Порядок блокировок завершения оплаты в B2 неполон. Когда счёт становится
оплаченным, `_sync_orders_after_bill_paid` начисляет бонусы за оплаченный
заказ через `apply_bonus_programs`, который блокирует строку гостя. Поэтому
фактический порядок — `Bill → Order → GuestProfile → BillingRequest →
TableSession`, и `pay_bill_with_bonuses` следует тому же префиксу. Новые
команды, затрагивающие эти строки, должны сохранять этот порядок. С B3.2
часть B в конец добавлен `TableVisit`: `… → TableSession → TableVisit`.

На тот момент в репозитории было два теста конкурентности только для
PostgreSQL (`apps/orders/test_concurrency.py`, `apps/tables/test_concurrency.py`).
Распределение по счёту, списание и начисление бонусов имели только
характеризующие тесты на SQLite; покрытие PostgreSQL для них добавлено в
B3.1. Открытые дефекты жизненного цикла, найденные после B3 (AA-020–AA-022),
ведутся в реестре аудита и батчах B3.1/B3.2.

## B3.2 часть A — изменения счёта (2026-10-23)

Исправления счетов следуют этому ADR: это явные команды
(`remove_bill_lines`, `void_bill`, `cancel_order`) с исполнителем, правом,
причиной и `BillAdjustment` только на дописывание; убранные строки
деактивируются, а не удаляются. Порядок блокировок: `Bill → BillItem →
GuestProfile → Order`. Отмена заказа через любой адаптер отклоняется, пока у
заказа есть активные строки счёта.
