# ADR-0003: Money и lifecycle меняются только через guarded commands

**Статус:** Accepted  
**Дата:** 2026-07-27

## Контекст

Аудит обнаружил несколько независимых путей изменения критичных данных: стандартные формы Django Admin позволяют менять `Order`, `Bill`, `BillingRequest`, `TableSession`, campaign и ledger-подобные записи; action для `BillingRequest` использует queryset `.update()` и допускает обратные переходы. При этом domain services содержат часть нужных проверок. Есть подтверждённые конкурентные риски: stale `Order` transition без locked reload, две активные session для guest и одна `OrderItem` в двух bill allocation. Повторный bonus redemption может не сериализоваться на guest balance.

## Решение

Для финансовых и lifecycle-сущностей установить единый command boundary:

* разрешённый state transition определяется явно и выполняется service/policy владельца;
* command получает текущие строки через `select_for_update()` в стабильном порядке и фиксирует idempotency/correlation key, если вызов повторяемый;
* financial ledger append-only, изменение balance — часть той же guarded command;
* allocation позиции счёта имеет один активный владелец, защищённый lock-ом и DB-level strategy после миграции данных;
* Django Admin отображает финальные/lifecycle-поля read-only; разрешённые операции выполняются явно названными action-ами, вызывающими тот же command, с actor и reason;
* прямые model save, inline edit и queryset `.update()` не являются допустимыми обходами.

## Последствия

Положительные:

* notification/history/total не расходятся между bot и Admin;
* повтор callback/task-а не создаёт новый экономический эффект;
* audit trail можно сопоставить с actor и причиной.

Ограничения:

* Admin UX становится менее свободным и потребует специальных action/forms;
* lock contention и idempotency storage должны быть измерены и покрыты тестами;
* существующие модели не меняются все сразу: необходимы маленькие migration batches с rollback.

## Область и проверка

Первыми покрываются order status, billing request, bill allocation/payment, bonus redemption и table session. Для каждого use case нужны tests: неразрешённый переход, double submit, параллельный запрос в PostgreSQL, невозможность Admin bypass и корректный rollback при ошибке. Изменение считается завершённым, только если public bot/Admin path вызывает один command и DB/data invariant проверен.

## B2 implementation update — 2026-08-06

B2 establishes the following concrete lifecycle boundaries without changing
the public command names:

* `transition_order_status()` reloads the canonical `Order` under
  `select_for_update()` before checking the transition, writing history, or
  scheduling post-commit notifications. A repeated callback is rejected from
  the current state rather than being applied from a stale object.
* Table-session activation locks in the order `GuestProfile → Table → active
  TableSession rows`. The guest lock serializes two QR scans for different
  tables; the new partial unique constraint
  `unique_active_table_session_per_partner_guest` is the durable guard, and the
  existing latest-scan-wins behavior is preserved by closing the previous
  active session before creating the new one.
* Session close, bill issue/payment, and billing-request transitions reload
  and lock their canonical row before validating state. Payment completion
  proceeds `Bill → Order → BillingRequest → TableSession`; notification and
  Telegram effects remain post-commit or task-backed.
* Order/cart/bill/allocation/session Admin forms expose lifecycle, relation and
  derived fields as read-only. The approved state operations are explicit
  actions that call the owning order, billing, or table-session service;
  `BillingRequestAdmin` no longer uses queryset `.update()`.

Before creating the session constraint, the current local SQLite data audit
found 2 active sessions and 0 duplicate `(partner, guest)` active scopes.
Production rollout must run the same duplicate query before applying the
migration; no data repair is performed by this batch. PostgreSQL-only
concurrency tests are included but could not run in the local environment
because no PostgreSQL/Docker daemon was available.

## B3 payment-flow clarification — 2026-08-06

The bonus-payment command is a single staff/service intent rather than a
separate “redeem, then settle zero-total bill” Admin workflow:

* `pay_bill_with_bonuses()` locks `Bill → Order → GuestProfile`, validates the
  partner-scoped ledger balance, and applies the maximum amount allowed by the
  partner's active programme at a 1:1 bonus-to-UAH rate.
* If bonuses do not cover the bill, the command persists the redemption and
  leaves the remaining monetary amount on the bill. Cash/terminal payment of
  that remainder causes the order payment method to be derived as mixed.
* If bonuses cover the bill completely, the same command creates the ordinary
  `Payment.Method.BONUSES` record for the nominal bonus value and closes the
  bill; `Bill.paid_amount` continues to represent money paid only. There is no
  `settle_zero_total_bonus_bills` Admin action and Admin cannot create bonus
  payments directly.
* Paid settlement remains the current baseline mapping for order rewards; the
  existing `ORDER_COMPLETED` value is compatibility naming, while partner-
  specific trigger expansion remains future programme work.
