# ADR-0006: Документация управляется как проверяемый контракт

**Статус:** Accepted  
**Дата:** 2026-07-27

## Контекст

До аудита несколько корневых документов одновременно претендовали на роль инструкции, продукта и текущего состояния. В `PROJECT_CHEATSHEET.md` зафиксированы устаревшие результаты тестов/lint и локальные абсолютные пути; `TABLEOS_TZ.md` содержит широкую целевую спецификацию, часть которой не реализована или расходится с кодом. Документация без статуса создаёт риск, что contributor воспринимает legacy statement как runtime fact.

## Решение

Ввести single-source-of-truth структуру:

* `README.md` — короткий вход и ссылки;
* `AGENTS.md` — обязательные guardrails разработки;
* `docs/product/` — canonical product specification, feature matrix, open decisions и migration map legacy TZ;
* `docs/architecture/` — AS-IS, target boundaries/layering/tenancy/runtime;
* `docs/decisions/` — ADR для значимых решений;
* `docs/engineering/` — setup, style, test/deploy workflow;
* `docs/audits/` — воспроизводимые baseline, coverage, findings и roadmap.

Каждый документ помечает status/owner/source of truth. Legacy-документы сохраняются как evidence и получают явную ссылку на canonical replacement; противоречия фиксируются с code evidence, а не исправляются молча. Изменение runtime/business rule требует в том же change обновить canonical doc, tests и ADR, если меняется решение, а не только реализация.

## Последствия

Положительные:

* новый участник понимает, какой документ нормативный;
* audit conclusion воспроизводим и не смешивается с продуктовой фантазией;
* documentation drift становится наблюдаемой частью review.

Ограничения:

* у документа есть владелец и обязанность обновления;
* любые ссылки на локальные абсолютные пути и секреты/пароли должны устраняться из canonical docs;
* legacy TZ не может быть тихо переписано так, чтобы потерять исходное требование.

## Область и проверка

Применяется ко всем документам репозитория. В review проверяются: правильная canonical ссылка, отсутствие неподтверждённых «готово» утверждений, отсутствие локальных путей/секретов, ссылка на audit finding при известном расхождении и обновление feature matrix для пользовательского изменения. Перед завершением governance batch запускается link/path scan и сверка с фактическими test/check baseline.
