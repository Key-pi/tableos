# ADR-0007: Счёт и закрытие стола ограничены визитом

**Статус:** Accepted (продуктовое решение владельца); реализовано в B3.2 part B (`docs/architecture/B3_2_VISITS_AND_BILL_CHANGES.md`)\
**Дата:** 2026-10-23  
**Связано:** AA-020, AA-021, PQ-026, PQ-027, PQ-007 (остаётся открытым)

## Контекст

Сейчас «контекст счёта» — это стол целиком. `get_table_billable_orders`
выбирает все заказы стола, которые ещё не попали в счёт, за всё время;
`_close_table_sessions_if_fully_settled` (до B3.1) и кнопка «Запросить счёт» тоже
смотрят на всю историю стола. Неоплаченные заказы ушедших гостей попадают в
общий счёт следующей компании, а автозакрытие стола перестаёт срабатывать
навсегда (AA-020). Отдельной сущности «компания за столом» в модели нет:
есть только `TableSession` одного гостя.

## Решение

1. Вводится понятие **визит стола** — группа гостевых сессий, которые
   сидят за одним столом как одна компания. Каждая `TableSession` принадлежит
   ровно одному визиту; у стола может быть несколько активных визитов.
2. При сканировании QR, если за столом уже есть активный визит других
   гостей, бот спрашивает: **подсесть** к этому визиту или **начать новый**.
   Если активного визита нет, новый визит создаётся без вопроса. Повторное
   сканирование гостем, который уже в визите, возвращает его в тот же визит.
3. «Начать новый» не закрывает старый визит. Старый визит остаётся активным,
   стол помечается для персонала как имеющий несколько визитов, и сотрудник
   закрывает старый визит вручную по обычным правилам расчёта.
4. Общий счёт включает только заказы сессий своего визита; персональный —
   только заказы гостя в рамках текущего визита. Заказы одного визита никогда
   не попадают в счёт другого.
5. Автозакрытие после оплаты (если включено у партнёра) закрывает только те
   сессии, все заказы которых оплачены рассчитанными счетами. Сессии с
   неоплаченными заказами или без заказов остаются открытыми. Шаг
   автозакрытия никогда не блокирует и не откатывает запись оплаты.
6. Кнопка «Запросить счёт» и проверки «стол рассчитан» тоже считаются по
   визиту, а не по истории стола.

## Последствия

Положительные:

* гость не платит за чужие и старые заказы;
* стол можно рассчитать и закрыть частями, по компаниям;
* оплата больше не зависит от состояния чужих сессий.

Ограничения:

* нужна новая модель и миграция с заполнением визитов для существующих
  активных сессий (для исторических — по одной сессии на визит или по
  правилу, выбранному после аудита данных);
* в боте появляется шаг выбора при сканировании и экран/уведомление для
  персонала о столе с несколькими визитами;
* PQ-007 (гость пересаживается за другой стол с неоплаченными заказами) этим
  решением не закрывается и остаётся открытым.

## Область и проверка

Перед реализацией — characterization-тесты, воспроизводящие AA-020 и AA-021.
Реализация: модель визита и миграция (обратимая, после аудита данных),
выбор визита в `activate_table_session` и в боте, перевод выборок счёта,
кнопки запроса счёта и автозакрытия на визит. Проверки: две компании за одним
столом с неоплаченным заказом первой; подсадка к визиту; автозакрытие при
частично рассчитанном столе; конкурентное сканирование на PostgreSQL.
