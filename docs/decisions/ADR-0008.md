# ADR-0008: Гарантии доставки — рассылки не больше одного раза, рабочие уведомления хотя бы один раз

**Статус:** Accepted (решение владельца 2026-10-23); реализовано в B4\
**Дата:** 2026-10-23\
**Связано:** PQ-014, PQ-015, AA-008, AA-030, AA-018

## Контекст

Telegram не принимает ключ идемпотентности: если воркер упал после того, как
Telegram принял сообщение, но до записи результата в базу, система не может
узнать, дошло ли сообщение. «Ровно один раз» поэтому невозможно; нужно
выбрать, чем жертвовать — дублями или потерями.

До B4 рассылка отправляла сообщения внутри транзакции базы данных, без записи
о получателе и без защиты от повторного запуска задачи (AA-008); задачи
уведомлений повторяли уже отправленное и не проверяли, работает ли ещё
сотрудник (AA-030).

## Решение

1. **Рассылки — не больше одного раза на гостя и кампанию (PQ-014).**
   Аудитория записывается строками `BroadcastDelivery` (уникально по кампании
   и гостю) в момент старта. Пачка захватывается в короткой транзакции
   (`pending → sending`), отправка идёт без открытой транзакции, каждый
   результат записывается своей короткой транзакцией. Строка в `sending`
   никогда не захватывается повторно; если её воркер умер, восстановление
   помечает её `unknown`. Неоднозначные ошибки Telegram (сеть, 5xx) тоже
   `unknown`, без повтора. Перед отправкой заново проверяется, что гость не
   отписался и не заблокировал бота (иначе `skipped`).
2. **Рабочие уведомления персоналу и гостям — хотя бы один раз (PQ-015).**
   Временные ошибки Telegram повторяются задачей Celery (до 5 раз с
   паузами), задачи подтверждаются после выполнения (`acks_late`), поэтому
   при падении воркера уведомление может прийти дважды. Уже отправленное
   уведомление персоналу повторно не отправляется. Перед отправкой
   проверяется, что сотрудник и пользователь активны и не отключили
   уведомления.
3. Процессы: web, worker (очереди `default` и `broadcasts`; с 2026-10-26 в
   Docker это два сервиса — `worker` и `broadcasts`, AA-044), ровно один beat,
   ровно один bot, PostgreSQL, Redis — все объявлены в `docker-compose.yml`.

## Последствия

Положительные:

* гость не получает одну рекламу дважды ни при повторе задачи, ни при
  параллельных воркерах, ни при падении;
* официант узнаёт о заказе даже при временном сбое Telegram;
* счётчики кампании считаются по строкам доставки и сходятся после сбоев.

Ограничения:

* при редком падении воркера часть гостей рассылку не получит (`unknown`,
  видно в Admin и в `unknown_count`);
* рабочее уведомление может прийти дважды;
* повторный запуск кампании доходит только до тех, кому ещё не пытались
  отправить; ошибочные адресаты автоматически не повторяются.
