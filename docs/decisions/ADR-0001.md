# ADR-0001: Сохранять TableOS модульным монолитом

**Статус:** Accepted  
**Дата:** 2026-07-27

## Контекст

TableOS уже является одним Django-проектом с общей PostgreSQL-моделью, aiogram bot и Celery. Доменные области `orders`, `billing`, `bonuses`, `tables`, `employees` и `notifications` тесно разделяют tenant, lifecycle и транзакционные инварианты. Аудит нашёл проблемы на границах этих областей: отсутствие строгой проверки общей принадлежности `Partner`, конкурирующие изменения заказа/счёта и обход domain services через Admin. Вынос кода в сервисы сейчас не устраняет эти проблемы и добавляет distributed transactions, новые точки отказа и операционную стоимость.

## Решение

Оставить один развёртываемый модульный монолит:

* Django ORM и PostgreSQL остаются транзакционным source of truth;
* приложения сохраняют предметные границы и публичные application API;
* `bot`, Django Admin, Celery tasks и management commands являются adapter-ами;
* правила денег, статусов, tenant scope и authorisation живут в application/domain layer владельца данных;
* новая абстракция (`repository`, `interface`, `policy`, `rule`, `engine`) появляется только при нескольких реальных потребителях и отдельной ответственности.

Граница модуля не является сетевой границей. Межмодульное взаимодействие в пределах монолита использует documentированный Python API и короткие локальные транзакции.

## Последствия

Положительные:

* денежные и lifecycle-инварианты можно проверять в одной БД-транзакции;
* нет необходимости вводить saga, distributed lock или межсервисную согласованность;
* можно исправлять риски малыми обратимыми batch-ами.

Ограничения:

* прямые импорты и модели другого приложения должны контролироваться правилами слоёв;
* нельзя выдавать «модульность» за пустые файлы интерфейсов или косметические репозитории;
* если позднее понадобится независимое масштабирование, это потребует нового ADR с нагрузочными и ownership evidence.

## Область и проверка

Применяется ко всем новым и изменяемым use case. До каждого рефакторинга команда сверяет изменение с `docs/architecture/TARGET_ARCHITECTURE.md`, проверяет отсутствие новых циклических импортов и сохраняет совместимость публичных import paths. Любое предложение о выделении сервиса требует отдельного ADR, измеримых причин и плана миграции данных/операций.
