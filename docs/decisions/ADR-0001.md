# ADR-0001: Сохранять Botera Shop модульным монолитом

**Статус:** принято
**Дата:** 2026-07-27 (решение принималось, когда продукт назывался TableOS)

## Контекст

Botera Shop — один проект Django с общей моделью данных в PostgreSQL, ботом на aiogram и Celery. Доменные области `orders`, `billing`, `bonuses`, `tables`, `employees` и `notifications` тесно разделяют инварианты партнёров, жизненного цикла и транзакций. Аудит нашёл проблемы на границах этих областей: нет строгой проверки общей принадлежности `Partner`, конкурирующие изменения заказа и счёта, обход доменных сервисов через Admin. Вынос кода в сервисы сейчас не устраняет эти проблемы и добавляет распределённые транзакции, новые точки отказа и эксплуатационные расходы.

## Решение

Оставить один развёртываемый модульный монолит:

* Django ORM и PostgreSQL остаются транзакционным источником правды;
* приложения сохраняют предметные границы и публичные API приложения;
* `bot`, Django Admin, задачи Celery и management-команды — адаптеры;
* правила денег, статусов, границ партнёра и прав живут в слое приложения и домена у владельца данных;
* новая абстракция (`repository`, `interface`, `policy`, `rule`, `engine`) появляется только при нескольких реальных потребителях и отдельной ответственности.

Граница модуля — не сетевая граница. Взаимодействие модулей внутри монолита использует задокументированный Python API и короткие локальные транзакции. Связь с другими продуктами сети Botera — только через API и события и никогда не обязательна для заказа или оплаты (`docs/product/ECOSYSTEM_DIRECTION.md`).

## Последствия

Положительные:

* денежные инварианты и инварианты жизненного цикла можно проверять в одной транзакции базы;
* не нужно вводить саги, распределённые блокировки и межсервисную согласованность;
* риски можно исправлять малыми обратимыми батчами.

Ограничения:

* прямые импорты и модели другого приложения должны контролироваться правилами слоёв;
* нельзя выдавать «модульность» за пустые файлы интерфейсов или косметические репозитории;
* если позже понадобится независимое масштабирование, нужен новый ADR с доказательствами по нагрузке и владению.

## Область и проверка

Применяется ко всем новым и изменяемым сценариям. До каждого рефакторинга изменение сверяется с `docs/architecture/TARGET_ARCHITECTURE.md`, проверяется отсутствие новых циклических импортов и сохраняется совместимость публичных путей импорта. Любое предложение выделить сервис требует отдельного ADR, измеримых причин и плана миграции данных и эксплуатации.
