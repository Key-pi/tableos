# ADR-0002: Tenant isolation обеспечивается на нескольких уровнях

**Статус:** Accepted  
**Дата:** 2026-07-27

## Контекст

`PartnerBoundModel` добавляет `partner`, но сам по себе не доказывает, что связанные `guest`, `table`, `session`, `order`, `bill`, `menu item` и staff-профиль принадлежат одному partner. Аудит подтвердил, что normal bot flows обычно scope-ят запросы, но generic services и Admin/inlines допускают или потенциально допускают кросс-tenant связи. Также staff resolver проверяет `EmployeeProfile.is_active`, не всегда `User.is_active`; status partner-а проверяется при старте runtime, а не обязательно при каждом действии.

## Решение

Принять defence-in-depth tenant model:

1. Application command выводит `partner` из авторизованного actor/context и валидирует все связанные объекты против него.
2. Все selectors и Admin queryset/foreign key/inline поля выполняют scoped filtering в точке чтения.
3. Staff action требует active `User`, active employee profile, согласованную partner связь и текущую capability; callback не является доказательством доступа.
4. Runtime re-checks status/capabilities на update/action boundary, в том числе для `suspended` partner. B1 policy: suspended partner receives `Работа бота приостановлена, ожидайте обновлений.`, while a live-disabled `BotInstance` processes no update; polling transport ends on process restart.
5. Telegram ID rebinding and direct `TelegramAccount` Admin mutation are superuser-only. A venue owner, or a tenant editor with the `Employees` section permission granted by that owner, may change their employee's `@username` and partner-scoped profile data; the owner may update that venue user's username/name through scoped `UserAdmin`. Because `@username` is stored on a shared identity, its cross-context display effect is explicitly owner-approved. Telegram update synchronization remains a trusted system path.
6. Для существенных межтабличных связей вводится PostgreSQL enforcement после data audit и отдельной миграции. Поскольку обычный `CheckConstraint` не проверяет другую таблицу, точный механизм (составной FK, trigger constraint либо денормализованная проверяемая owner-column) выбирается и тестируется в migration batch.

## Последствия

Положительные:

* ошибка одного adapter-а не создаёт cross-tenant data exposure/write;
* правовая и бизнес-проверка доступа становится одинаковой для bot и Admin;
* legacy data получает явную проверку до ужесточения БД.

Ограничения:

* появятся явные параметры actor/partner и дополнительные тестовые fixture;
* DB enforcement может потребовать backfill, quarantine или remediation уже существующих строк;
* нельзя считать наличие `partner_id` на каждой модели достаточным доказательством isolation.

## Область и проверка

Сначала создаются characterization tests для cross-partner command, inactive user, suspended partner, Admin queryset/list-filter/inline choices и stale callback. Затем каждая миграция запускается на PostgreSQL с audit query до и после. Scope завершён, когда эти тесты зелёные, DB constraint strategy документирована и нет альтернативного unscoped write path.
