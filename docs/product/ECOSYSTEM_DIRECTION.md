# Botera — направление экосистемы

**Статус:** решения владельца от 2026-10-23; сверено с кодом на `65c2c41`.\
**Зачем:** чтобы любая работа в этом репозитории учитывала, частью чего он
становится. Документ не описывает реализованное поведение — оно в
[AS_IS_ARCHITECTURE.md](../architecture/AS_IS_ARCHITECTURE.md).

## Названия и продукты

| Имя | Что это | Где живёт |
|---|---|---|
| **Botera** | сеть и бренд всей экосистемы | — |
| **Botera Shop** | этот репозиторий (бывший TableOS): бот и Admin одного бизнеса — заведения или магазина | этот репозиторий |
| **Botera Master** | продукт для мастеров и частных специалистов | отдельный проект, уже в разработке |
| **Partnership** | партнёрские программы между бизнесами Shop и Master | будущий отдельный сервис |
| **Botera Discovery** | общий Telegram-бот-каталог бизнесов сети | будущий отдельный сервис |

Имя «TableOS» уходит. Переименовываем то, что видят люди: тексты бота,
Admin, документацию, репозиторий. Внутренние имена в коде и базе
(`tableos` в `pyproject.toml`, имена Python-пакетов, таблиц, Celery app) не
трогаем без отдельной причины: пользы нет, риск миграций реальный.

## Стол — одна из функций, а не основа

Заказ не обязан идти через стол и QR-код. Каналы заказа — модули,
включаемые партнёру:

1. **за столом** (QR, визиты, счета) — есть;
2. **самовывоз** — есть с 2026-10-23 (предоплата переводом,
   [PICKUP.md](../architecture/PICKUP.md));
3. **доставка** — есть с 2026-10-23 (адрес, цена, предоплата переводом,
   [DELIVERY.md](../architecture/DELIVERY.md));
4. **отправка** (почтовые службы, ТТН) — после доставки.

Что в коде уже готово к этому: `Order.table` и `Order.table_session`
необязательны; `PartnerBotSettings.module_pickup_enabled`,
`module_delivery_enabled` и подписи кнопок существуют, а
`PartnerBotSettings.clean` требует хотя бы один канал для модуля заказов.
Чего нет: самих сценариев. Сильнее всего к столу привязаны счета (строятся
от визита стола, ADR-0007) — каналы без стола требуют своего пути оплаты.

## Правила для работы в этом репозитории

- Botera Shop остаётся самостоятельным продуктом. Никаких импортов моделей
  Botera Master или других сервисов, никакого чтения чужих таблиц.
- Внешнее взаимодействие — только через API и события с `event_id` (UUID);
  обработчики на обеих сторонах идемпотентны.
- Partnership и Discovery никогда не обязательны для основной операции:
  заказ, оплата, визит завершаются без них; события копятся и
  доотправляются (тот же приём, что доставка рассылок в B4, ADR-0008).
- Наружу отдаём только UUID (они уже везде: `core/database/models.py`).
- Сложную инфраструктуру (брокеры, Kubernetes, отдельные серверы) не
  добавляем без измеримой причины. Всё может жить на одном VPS.

## Сверка с кодом: что уже есть для сети

| Нужно сети | В коде |
|---|---|
| UUID бизнеса, клиента, событий | есть: все модели на UUID |
| Telegram ID как общий ключ клиента | есть: глобальный `TelegramAccount.telegram_id`, свой `GuestProfile` у каждого партнёра |
| Много ботов в одном процессе | есть: `BotInstance` с зашифрованным токеном, один процесс `runbot` (polling; webhook — при сотнях ботов) |
| Источник перехода (`start=src_…`) | есть: `TrafficSource`, `SourceVisit` (PQ-031) |
| Исходящие события для Partnership (outbox) | нет; появится вместе с Partnership |
| Публичная карточка бизнеса для Discovery | нет |
| Самостоятельное подключение бизнеса | нет: партнёра и бота заводят через Admin |

## Партнёрские программы (по демо владельца)

Суть — **обмен условиями между бизнесами, хитрая взаимная реклама**:
выполнил условие у одного партнёра — получил награду у другого, и наоборот.
Например: три визита к мастеру → бонус в кальянной; два кальяна → скидка
у мастера.

- Бизнес публикует **открытую умову** («3 визита на маникюр за 60 дней»,
  видна всем партнёрам Botera) или шлёт **прямую пропозицию** конкретному
  партнёру.
- Партнёры отвечают своей наградой («−10% на Premium Hookah», «капучино в
  подарок»); автор принимает или отклоняет. Связи гибкие: мастер ↔
  заведение, заведение ↔ заведение, мастер ↔ мастер.
- Каждый бизнес выдаёт награду у себя, а взамен получает клиентов
  партнёра.
- Клиент просто пользуется ботами; прогресс по умове («3 / 3 визита») он
  видит в боте бизнеса.

Для Botera Shop это значит в будущем: отдавать события (`visit.completed`,
`order.completed`, `payment.completed`) и уметь применить партнёрскую
награду в счёте. Делается вместе с Partnership, не раньше.

## Порядок работ

1. B5 — чистка и гигиена — сделано.
2. Перед запуском: самовывоз, переименование видимого в Botera Shop, учёт
   источника перехода — сделано.
3. Доставка — сделана.
4. После: отправка, интеграция с Partnership, карточка для Discovery,
   самостоятельное подключение бизнеса.
