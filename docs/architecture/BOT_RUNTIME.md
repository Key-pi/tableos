# Botera Shop — работа бота и граница обработчиков

**Статус:** текущая карта работы бота и целевые ограничения.

## Текущая схема

Команда `manage.py runbot` запускает сервис ботов
`bot/supervisor.py:BotSupervisor`; с `--processes N` — N таких процессов,
каждый бот ровно в одном (`bot/services/runtime.py:configs_for_shard`,
AA-043). Подробно — раздел «Сервис ботов» ниже. `bot/main.py:create_dispatcher` регистрирует
`PartnerRuntimeMiddleware` как внешний middleware и подключает роутеры в
порядке `start → session → menu → order → remote_checkout → profile →
billing → guest_call → staff`. aiogram выбирает первый подходящий
обработчик, поэтому порядок роутеров и текстовые фильтры — это видимое
поведение.

| Вопрос | Как сейчас | Правило |
|---|---|---|
| Определение партнёра | партнёр выбирается по токену бота; с B1 перед обработкой заново проверяются состояние партнёра и экземпляра бота | приостановленный партнёр получает стандартный ответ «работа приостановлена»; отключённый экземпляр бота молча пропускается |
| Сборка роутеров | статическое подключение в `bot/main.py` | регистрация нового роутера — пункт ревью «динамический потребитель» |
| Подписи кнопок | точное совпадение с подписью на любом языке (каталог и свои тексты заведения), `bot/filters/content.py`; ответы на ForceReply узнаются по началу подсказки на любом языке (`core.i18n.variants`) | подписи действий одного языка не совпадают (`BotText.clean`, тест разных языков каталога); стабильный callback — где неоднозначность нельзя устранить |
| Данные callback | обработчик находит запись домена/сотрудника | идентификатор в callback — не доказательство прав; заново загружать текущее состояние с учётом партнёра |
| Доступ к ORM | обработчики оборачивают работу с Django в `sync_to_async`; все такие вызовы процесса идут через один поток по очереди, поэтому процесс использует одно ядро | сохранять неблокирующий адаптер; не помещать бизнес-инварианты в обработчик; больше ядер — больше процессов (`runbot --processes`), а не потоков: ORM-код держит GIL |
| Список ботов | сервис перечитывает его раз в минуту (`--reload-interval`), состояние каждого бота — в `BotInstance.runtime_state` (PQ-041, PQ-042) | список — только какие боты опрашивать; статус партнёра и бота всё равно проверяется на каждом обновлении |
| Форматирование | все сообщения бота и уведомления в `ParseMode.HTML`; с B3.1 динамические значения проходят через `bot/utils/html.py:escape_html` (бот) или `_escape_html` (уведомления) | экранировать каждое подставляемое значение (партнёр, меню, гость, сотрудник, комментарий) при отрисовке; подписи кнопок не экранировать; разметку могут содержать только шаблоны партнёра и тексты рассылок |
| Загрузки на каждое обновление | middleware проверяет бота и партнёра, загружает язык и свои тексты заведения; обработчики этого же обновления берут проверенного партнёра (`bot/services/context.py:partner_for_this_update`), свои тексты — из кэша, который сбрасывается при сохранении и удалении `BotText` (AA-047); около 20 запросов на обновление | статус партнёра и бота проверяется в начале каждого обновления; никогда не кэшировать статус, права, заказы, счета, оплаты, бонусы и визиты; новый кэш — только после замера и со сбросом при изменении |

## Сервис ботов (PQ-041, PQ-042)

Решения владельца 2026-11-04: неисправный бот не мешает остальным, его
причина видна в Admin; бот из Admin подключается сам в течение минуты; токен,
который Telegram перестал принимать, останавливает только свой бот.

`aiogram.Dispatcher.start_polling` для этого не годится: один неудачный
`getMe` останавливает всех ботов процесса, а отклонённый токен опрашивается
бесконечно. Поэтому `bot/supervisor.py:BotSupervisor`:

1. **Проверка раз в минуту** (`reconcile`). `scan_bot_configs` проверяет
   каждый активный бот отдельно и возвращает исправных и состояние каждого.
   Свои боты процесса берутся через `configs_for_shard`. Затем сервис
   останавливает убранных и выключенных ботов, перезапускает бота со
   сменённым токеном, обновляет карту токен → партнёр для middleware
   (`register_runtime_configs`) и запускает новых.
2. **Свой цикл на бота** (`_poll`). Каждый бот сам вызывает `getUpdates`.
   Первый запрос идёт с `timeout=0`: Telegram отвечает сразу, и Admin
   показывает «Работает» без ожидания длинного опроса. Дальше запросы идут
   с `timeout=30`. Обновление — отдельная задача
   (`dispatcher.feed_update`), ошибка одного обновления пишется в журнал и
   не останавливает бота. Диспетчер в процессе один (`shared_dispatcher`):
   роутеры aiogram подключаются только к одному.
3. **Ошибки Telegram:**

| Ответ | Что делает сервис | Состояние в Admin |
|---|---|---|
| `Unauthorized` (токен отозван) | останавливает только этот бот и не пробует снова, пока в Admin не сохранят другой токен | «Не запущен: Telegram не принимает токен — выпустите новый в @BotFather» |
| `Conflict` (токен опрашивает ещё одна программа) | повторяет с паузой 1–5 с; после удачного запроса состояние снова «Работает» | «Сбой: этот токен опрашивает ещё одна программа — остановите её» |
| сеть, 5xx, лимиты | повторяет с паузой | без изменений |

4. **Состояние** (`BotInstance.RuntimeState`, `runtime_checked_at`)
   записывается только при изменении (`record_bot_runtime_states`). Значения:
   работает; работает, но заведение приостановлено (PQ-013); демо-токен;
   токен с ошибкой; токен не расшифровывается; токен уже у другого бота;
   Telegram не принимает токен; конфликт; режим webhook. Выключенный бот
   показан как «Выключен».
5. **Остановка.** По `SIGTERM`/`SIGINT` сервис останавливает циклы, ждёт
   начатые обновления до 10 с и закрывает HTTP-сессии ботов.

`bot/main.py:run_polling` (обычный `start_polling`) остался для эмулятора и
нагрузочного теста. Тесты сервиса — `bot/tests_supervisor.py`, на
поддельном боте без сети.

## Договор обработчика

Обработчик делает только следующее:

1. разбирает и проверяет обновление Telegram и известную схему callback;
2. определяет текущего партнёра и текущий контекст исполнителя/гостя;
3. вызывает один сервис или селектор владельца с идентификаторами и
   контекстом, ограниченными партнёром;
4. переводит типизированный результат или контролируемую доменную ошибку в
   интерфейс Telegram.

Обработчики не меняют модели ORM напрямую, не решают межмодульные денежные
правила и не считают ранее созданную клавиатуру доказательством прав.
Клавиатура может прятать недоступные действия, но выполнение заново делает
ту же живую проверку.

## Зафиксированные особые случаи

- B1: `PartnerRuntimeMiddleware` выполняется перед каждым роутером и
  фильтром. Приостановленному партнёру отвечает «Работа бота
  приостановлена, ожидайте обновлений.» и показывает тот же текст во
  всплывающем ответе на callback. Отключённый на лету `BotInstance` молча
  пропускается; его опрос сервис останавливает на следующей проверке.
- B1: сотрудник определяется только при активном `User`, активном
  `EmployeeProfile` и совпадении партнёра. Устаревшие callback-и заказов
  заново проверяют текущее право на модуль заказов перед чтением или
  изменением заказа; формальная матрица ролей остаётся вопросом PQ-004.
- B1: `PartnerBotSettings.clean()` отклоняет повторяющиеся и пустые подписи
  кнопок с маршрутизацией. Маршрутизация по тексту кнопки остаётся;
  переход на стабильные намерения — вне того батча.
- B3.2 часть B: активация по QR может ответить выбором визита (`tv:j:<визит
  hex>` — подсесть, `tv:n:<стол hex>` — новый). Callback не несёт токен QR;
  обработчик заново загружает стол в пределах партнёра бота, а сервис
  проверяет, что визит активен и принадлежит столу, иначе гость видит
  «Выбор устарел. Отсканируйте QR-код стола ещё раз.». Действия персонала
  с визитами (`stafftvshared`, `stafftvpersonal`, `stafftvclose`) заново
  загружают визит в пределах партнёра сотрудника.
- Удалённое оформление (самовывоз и доставка; PICKUP.md, DELIVERY.md, ADR-0009): шаги гостя —
  callback-и без состояния `rc:<код канала>:…` (`p` — самовывоз);
  последний `rc:p:p:…` несёт итог и сумму к оплате, которые видел гость, и
  сервис не создаёт заказ, если что-то изменилось. Способ заказа выбирается
  сначала (кнопка «Самовывоз» или скан QR стола) и хранится в
  `Cart.channel`; корзина стола предлагает `cart:mode:pickup`, а вернуться
  к заказу за столом можно только повторным сканированием QR. Присланный
  контакт принимается, только если `contact.user_id` — сам отправитель.
  Действия персонала `stafftxok`, `stafftxno` (сначала переспрашивает) и
  `stafftxnoy` заново загружают заказ в пределах партнёра сотрудника;
  сервис проверяет роль (владелец, менеджер, кассир).
- Бот сети (PQ-047, [NETWORKS.md](NETWORKS.md)). `PartnerRuntimeMiddleware`
  для бота сети (`Network.bot`) сначала выбирает точку обновления
  (`bot/services/network.py`). Без точки он спрашивает «📍 В какое
  заведение?» (`point:<hex>`) и обработчики не вызывает. С точкой
  обработчики работают как в собственном боте точки. Middleware запросов
  `bot/middlewares/message_points.py` запоминает точку каждого
  отправленного сообщения, чтобы его кнопки действовали для неё. Смена
  точки — `bot/handlers/points.py` (кнопка «📍 Заведение», `/point`).
- Приглашения сотрудников (PQ-046, `bot/handlers/staff_invites.py`): `/start
  inv_<код>` разбирает `start_handler` до QR стола и источников. Callback-и
  `staffinv` (роли), `staffinv:r:<роль>` (выдать ссылку),
  `staffinv:y:<hex>` / `staffinv:n:<hex>` (решение). Каждый заново находит
  сотрудника и проверяет право через `apps/employees/invites.py`. Сообщения
  выдавшему и новому сотруднику собираются на языке получателя
  (`speaking_to_employee` / `speaking_to_guest`); подписи клавиатуры
  нового сотрудника — тоже: `BotContent` строится внутри его языка.
- Способы оплаты (PQ-033, PAYMENT_OPTIONS.md): выбор гостя —
  `rc:<c>:m:<slot>:<0|1>:<t|r>`, способ едет последним сегментом
  `rc:<c>:p:…:<t|r>` (без него — перевод, для итогов, отправленных раньше);
  сервис отказывает в способе, который владелец не включил. Оплата при
  получении у персонала — `staffrccash`, `staffrccard`, `staffrcno`
  (переспрашивает) и `staffrcnoy`; заказ загружается заново в пределах
  партнёра, роль проверяет сервис.
- Доставка (PQ-032): код канала `d`. Адрес — свободный текст, поэтому
  бот просит его сообщением с ForceReply «🏠 Адрес доставки»; ответом на это
  сообщение считается только текст, отвеченный именно на него
  (`remote_checkout.py:_is_address_answer`), состояние не хранится.
  Сохранённый адрес предлагается кнопками `rc:d:a:ok` / `rc:d:a:new`.
  Геолокация (`location_handler`) сохраняется, только если корзина гостя
  на доставку.
- Возвраты (PQ-037): кнопка «↩️ Возврат» в карточке оплаченного заказа →
  `strf:<заказ>:<маска>` (выбор строк; маска — шестнадцатеричные биты строк
  заказа в его оплаченном счёте) → `strr` (причина) → `strm` (как вернули) →
  `strc` (итог) → `strk` (выполнить). Состояние только в callback; право,
  счёт и строки перепроверяет сервис под блокировками
  (`bot/handlers/staff_refunds.py`).
- Язык гостя (PQ-040): «🌐 Язык» в профиле → `guestlang:menu`; выбор —
  `guestlang:<uk|ru|en>` или `guestlang:auto` (как в Telegram). Сервис
  `apps/users/services.py:set_guest_language` отказывает в языке, который
  заведение выключило. После выбора бот присылает главную клавиатуру на
  новом языке. Язык каждого обновления ставит `PartnerRuntimeMiddleware`
  ([LANGUAGES.md](LANGUAGES.md)).
- «Мои заказы»: `guestorders:<страница>` (список) и
  `guestorder:<номер>` (карточка). Обработчик:
  `bot/handlers/profile.py:my_orders_callback`.
  - Заказ ищется только среди заказов этого гостя у партнёра бота
    (`apps/orders/selectors.py:get_guest_orders`); чужой номер из callback
    даёт «Заказ не найден».
  - Фильтр — регулярное выражение, `guestorderconfirm:` в него не попадает.
- Отправка почтой (PQ-034): код канала `s`. Служба — `rc:s:c:<np|up|mm>`
  (сервис отказывает в выключенной), получатель — ответ на ForceReply
  «📦 Куда отправить» (`remote_checkout.py:_is_destination_answer`),
  сохранённый — `rc:s:a:ok` / `rc:s:a:new`; вместо времени — вариант
  пересылки `rc:s:t:<c|f>` (тот же сегмент, что время у других каналов).
  Персонал: `staffship:<заказ>` просит ТТН сообщением с ForceReply
  «📦 ТТН для заказа #…»; ответ на него
  (`staff.py:staff_tracking_number_handler`) перепроверяет сотрудника,
  заново загружает заказ в пределах партнёра и вызывает
  `remote_orders.py:mark_order_shipped`; ответ гостя на такое сообщение
  ничего не меняет. Наложенный платёж — `staffrccod:<заказ>`. Кнопка гостя
  «Получил(а)» в сообщении об отправке — тот же `guestorderconfirm:<заказ>`,
  без стола принимается только для своей отправки.
- Источники переходов (PQ-031): параметр `/start` вида `src_<код>` — ссылка
  источника, а не QR стола. Переход записывается, если у партнёра бота есть
  активный источник с таким кодом; в любом случае гость получает обычное
  приветствие. Код ищется только у партнёра этого бота.

## Схема callback и текстов

Использовать ключ действия с пространством имён и идентификатор объекта.
Сервис независимо загружает объект заново и проверяет права. Если действие
по тексту кнопки оставлено ради удобства, проверка настроек должна
доказывать, что оно в данном контексте соответствует ровно одному
включённому намерению. Переименование подписи не должно незаметно
превращать сохранённое или устаревшее сообщение пользователя в другую
команду.

## Проверка работы бота

Тесты и ручной обзор изменения, затрагивающего бота, покрывают:

- подключение и порядок роутеров и нужное первое совпадение;
- поведение для активного и приостановленного партнёра;
- неактивного пользователя/профиль и несовпадение партнёра;
- повтор callback и отзыв прав после отрисовки интерфейса;
- границу `sync_to_async` для работы с ORM и сервисами;
- совместимость изменённой схемы callback;
- отсутствие жёстко заданных текстов маршрутизации, конфликтующих с
  настройками партнёра.

Задачи описаны отдельно в [`BACKGROUND_JOBS.md`](BACKGROUND_JOBS.md); они
тоже адаптеры и не могут быть способом обойти сервис-владелец.
