# B3.2 — визиты стола, изменения счёта, база кешбэка

**Статус:** согласован владельцем 2026-10-23 (решения — в конце документа);
реализованы все три части: A (ветка `b3.2a-bill-changes`), B (ветка
`b3.2b-visits`), C (ветка `b3.2c-cashback`).\
**Основание:** ADR-0007, PQ-026, PQ-028, PQ-030, находки AA-020 и AA-022.\
**Порядок работ:** три независимые части, каждая отдельной веткой и с
отдельными миграциями: **A — изменения и аннулирование счёта** (самый большой
денежный риск), **B — визиты стола**, **C — база кешбэка**.

## A. Изменение и аннулирование счёта (PQ-028, AA-022)

### Что меняется для людей

- В карточке счёта (бот и Admin) появляются действия **«Убрать позицию»** и
  **«Аннулировать счёт»**. Их видят и выполняют только сотрудники с правом
  «Может изменять счета» и владелец заведения.
- Право выдаёт **только владелец**: галочка в профиле сотрудника в Admin;
  менеджеры её не видят и не меняют.
- Каждое изменение требует причину и попадает в историю счёта: кто, когда,
  что изменилось, сумма до и после.
- Отмена заказа, который уже лежит в неоплаченном счёте, автоматически убирает
  его позиции из счёта и пересчитывает сумму. Такая отмена требует того же
  права; без права бот объясняет, что нужно обратиться к менеджеру.
- Отменить заказ, который уже в оплаченном счёте, нельзя: возвратов в системе
  нет.

### Правила

| Правило | Как проверяется |
|---|---|
| Сумма счёта после изменения не меньше уже оплаченной суммы | в команде под блокировкой счёта |
| Оплаченный (`paid`) счёт не изменяется и не аннулируется | статус проверяется после блокировки |
| Аннулировать можно только счёт без денежных оплат | `paid_amount == 0` |
| Убранная позиция и позиции аннулированного счёта снова доступны для выставления | allocation становится неактивной |
| Счёт с применёнными бонусами менять нельзя — только аннулировать целиком (решение 1) | `bonus_spent_amount == 0` для удаления позиций и отмены заказа в счёте |
| Аннулирование счёта с бонусами возвращает гостю списанные бонусы отдельной записью в истории бонусов | новая операция ledger `reversal`, связанная со счётом |

### Модель данных

- `BillItem.is_active` (bool, по умолчанию `True`), `removed_at`,
  `removed_by`. Позиция не удаляется физически, а деактивируется, чтобы
  история сохранялась.
- Ограничение `unique_order_item_bill_allocation` становится условным:
  уникальность `(partner, order_item)` только для `is_active=True`. Миграция
  проверяет дубли до замены ограничения.
- Новая модель `BillAdjustment`: `bill`, `kind` (`remove_line`, `void`,
  `order_canceled`), `actor` (User), `reason_code`, `reason_text`,
  `total_before`, `total_after`, `payload` (id позиций), `created_at`.
  Только добавление записей; в Admin только просмотр.
- `EmployeeProfile.can_adjust_bills` (bool, по умолчанию `False`). В Admin
  поле редактируют только владелец заведения и superuser.
- Подсчёт сумм (`_compute_bill_totals`) учитывает только активные позиции.
- **Откат миграции `billing.0005`.** Обратная миграция возвращает
  безусловное ограничение `unique_order_item_bill_allocation`. Она упадёт,
  если после выкатки позиции аннулированного счёта уже выставлены заново
  (две строки на один `order_item`: неактивная и активная). Перед откатом
  такие неактивные строки нужно выгрузить и решить их судьбу вручную;
  автоматически миграция их не удаляет.

### Команды (владелец — `apps/billing/services.py`)

- `remove_bill_lines(bill, order_item_ids, actor, reason)` — блокировки
  `Bill → BillItem`, проверка права и правил, деактивация, пересчёт, запись
  `BillAdjustment`.
- `void_bill(bill, actor, reason)` — то же для всех позиций, статус
  `canceled`, связанные запросы счёта возвращаются в `open`, чтобы персонал
  видел, что гость ещё не рассчитан.
- `cancel_order(order, actor, reason)` убирает позиции заказа из открытого
  счёта (`kind=order_canceled`) и отменяет заказ. `transition_order_status`
  отказывается отменять заказ с активными позициями в счёте (проверка после
  блокировки заказа), поэтому обойти команду нельзя. Порядок блокировок:
  `Bill → BillItem → GuestProfile → Order`.

## B. Визиты стола (ADR-0007, PQ-026, AA-020)

### Что меняется для людей

- Гость сканирует QR. Если за столом нет активного визита, создаётся новый —
  как сейчас, без вопросов.
- Если за столом уже есть активный визит других гостей, бот спрашивает:
  «За этим столом уже сидит компания. Подсесть к ней или начать новый визит?».
  Кнопки: «Подсесть к компании (с 19:40, 3 гостя)» — по одной на каждый
  активный визит — и «Начать новый визит». Имена других гостей не
  показываются.
- Гость, уже состоящий в визите этого стола, при повторном сканировании
  возвращается в свой визит без вопроса.
- «Начать новый визит» не закрывает старый. Персоналу приходит уведомление
  «За столом #5 начат новый визит, предыдущий не закрыт», а в разделе
  «Столы» такой стол помечен ⚠. Сотрудник открывает старый визит и закрывает
  его: рассчитывает (счёт и оплата) или отменяет неоплаченные заказы (с правом
  из части A).
- Общий счёт, кнопка «Запросить счёт» и проверки «стол рассчитан» работают по
  визиту. Персональный счёт — заказы гостя в рамках текущего визита.

### Модель данных

- Новая модель `TableVisit` (`apps/tables`): `partner`, `table`, `status`
  (`active`/`closed`), `started_at`, `closed_at`, `closed_by`.
- `TableSession.visit` — FK, nullable (у исторических закрытых сессий визита
  нет).
- `Bill.visit` — FK, nullable (счета без стола и исторические счета).
- Несколько активных визитов на одном столе допустимы.

### Команды

- `activate_table_session` получает параметр `visit_choice` (`None` /
  `join:<visit_id>` / `new`). Если выбор нужен, а не передан, сервис
  возвращает результат «нужен выбор» со списком визитов вместо исключения.
  Блокировки: `GuestProfile → Table → TableVisit → TableSession`.
- Бот: callback `tv:j:<visit_id>:<table>_<token>` и `tv:n:<table>_<token>`.
  QR-токен повторно проверяется при нажатии; визит должен быть активным и
  принадлежать этому столу.
- `close_table_visit(visit, actor)` — закрывает визит и его сессии, если всё
  рассчитано; иначе объясняет, что мешает.
- `get_table_billable_orders` заменяется выборкой по визиту; автозакрытие из
  B3.1 после закрытия последней сессии визита закрывает и сам визит.

### Перенос данных

Аудит перед миграцией: число активных сессий по столам. Затем:

- активные сессии одного стола объединяются в один активный визит (сейчас
  система и так считает их одной компанией — см. вопрос 2);
- закрытые сессии остаются без визита;
- открытые счета получают визит, если все их заказы из сессий одного визита.

Миграция обратимая; данные при откате не удаляются.

### Как реализовано (отличия от плана)

- Выбор режима — параметр `visit_choice`: `ask` (бот), `auto` (по умолчанию
  для сервисов и тестов: подсесть к компании за столом, иначе новый визит),
  `new`, `join:<visit_id>`. При `ask` сервис бросает `VisitChoiceRequired`
  со списком вариантов, транзакция откатывается.
- Подсесть можно только к визиту, где сейчас сидит хотя бы один гость.
  Открытый визит без гостей (все ушли, остались неоплаченные заказы) — работа
  персонала, а не компания для подсадки.
- Callback-и короче плана, чтобы уложиться в 64 байта: `tv:j:<visit hex>`
  и `tv:n:<table hex>`. QR-токен при нажатии не передаётся: сервис заново
  проверяет стол, партнёра и что визит активен и принадлежит столу; если нет —
  «Выбор устарел. Отсканируйте QR-код стола ещё раз.».
- Блокировки: `GuestProfile → Table → свои TableSession гостя → TableVisit`
  (стол блокируется до визита: так сериализуются создание и подсадка).
  Закрытие визита после оплаты блокирует визит последним
  (`… → TableSession → TableVisit`).
- Визит закрывается сам, когда в нём никто не сидит и он рассчитан;
  `close_table_visit` — команда персонала (кнопка в карточке стола и действие
  в Admin).
- Кнопки «общий/персональные счета» уровня стола остаются только для
  заказов без визита (исторических); для визитов — свои кнопки
  (`stafftvshared`, `stafftvpersonal`, `stafftvclose`). Если визитов
  несколько, счёт стола без выбора визита запрещён.

## C. База кешбэка (PQ-030)

- `BonusProgram.accrual_base`: `full_total` (по умолчанию — как сейчас) или
  `money_paid`.
- Для заказа при `money_paid`: сумма заказа минус его доля бонусов счёта.
  Бонусы распределяются между заказами счёта пропорционально суммам, копейки
  округления — на последний заказ.
- Для быстрой продажи при `money_paid`: `amount − bonus_spent_amount`.
- Визитные и milestone-программы не меняются.

### Как реализовано

- Доля заказа считается по его активным позициям именно в этом счёте
  (`apps/billing/services.py:_bill_bonus_share_by_order`), а не по полной
  сумме заказа; сумма долей всегда равна `bill.bonus_spent_amount`.
  Начисление по-прежнему одно на заказ — при первой оплате счёта с ним.
- Порог `min_order_total` сравнивается с полной суммой покупки: режим меняет
  только базу начисления.
- Предпросмотр быстрой продажи у персонала показывает ожидаемое начисление
  с учётом выбранного списания бонусов.
- Режим хранится в программе и выбирается в Admin (поле «accrual base»).

## Проверка

Для каждой части: тест, который падает на текущем коде; полный набор на
SQLite и PostgreSQL 16; PostgreSQL-тесты конкурентности (одновременное
изменение счёта и оплата; два гостя одновременно сканируют стол с выбором
визита); прямой и обратный прогон миграций на копии данных.

## Решения владельца (2026-10-23)

1. **Бонусы и изменение счёта:** счёт, по которому списаны бонусы, нельзя
   менять по позициям — его можно только аннулировать целиком; при
   аннулировании бонусы возвращаются гостю (запись `reversal` в истории
   бонусов), после чего заказы выставляются в новый счёт.
2. **Перенос активных сессий:** все активные сессии стола объединяются в один
   визит.
3. **Причина изменения:** кнопки с готовыми причинами («Ошибка ввода»,
   «Отказ гостя», «Комплимент заведения», «Другое») плюс необязательный
   комментарий.
4. **Отмена заказа в неоплаченном счёте** требует права «Может изменять
   счета».
