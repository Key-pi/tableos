# Подключение к Poster (PQ-058) — план v1

**Статус:** план; решение владельца 2026-11-20 (ADR-0010); кода ещё нет.
Работа идёт по шагам ниже, каждый шаг проверяет владелец. Работа не ждёт
интервью с заведениями (владелец 2026-11-20).

Заведение работает на кассе Poster и подключает к ней Botera Shop: меню
приходит из Poster, заказы из бота — на кассу онлайн-заказами, гость узнаёт в
Telegram, принят ли заказ. Решение и его причины — [ADR-0010](../decisions/ADR-0010.md).

## Решения владельца 2026-11-20

- Границы v1 — как ниже в «Что входит»: только оплата при получении, бонусы в
  режиме Poster — с v2.
- Новая зависимость `httpx` для запросов к Poster — согласована.
- Работа идёт независимо от интервью с заведениями.

## Что входит в v1

- Подключение в один клик из Admin Botera: вход в Poster, выбор точки.
- Меню из Poster: категории, позиции, цены точки, варианты, добавки,
  видимость; обновление по вебхукам и ночью.
- Заказы самовывоза и доставки из бота уходят на кассу Poster онлайн-заказом
  (телефон, имя, адрес, время, комментарий, метка `Botera #<код заказа>`).
- Принят или отклонён на кассе → гость получает обычное сообщение о статусе.

Не входит в v1: бонусы на чеки Poster, предоплата переводом, заказы стола и
счета стола, продажа на кассе Botera, отправка почтой, экран кухни Botera,
вызов персонала, виджет на кассе Poster, установка из маркетплейса Poster.

## Как это видит владелец заведения

1. Admin → «Poster» → «Подключить Poster» → вход в свой аккаунт Poster и
   согласие → выбор точки (если их несколько).
2. Меню появляется в Botera; владелец добавляет фото, описания и переводы,
   отмечает способы заказа. Поля из Poster (название, цена, категория,
   варианты, добавки) в Admin только для чтения, с пометкой «из Poster».
3. Владелец выбирает товар Poster «Доставка» — им передаётся цена доставки.
4. Гость заказывает в боте как сейчас; на кассе появляется онлайн-заказ;
   кассир принимает его или отклоняет.
5. «Отключить Poster» — заказы больше не передаются, меню остаётся как было,
   его снова можно править в Botera.

## Устройство

Новое приложение `integrations.poster` — адаптер на краю, как бот и Admin:
вызывает сервисы заказа и меню и не повторяет их правила. Ядро счёта
(`apps/billing/services.py`) и модель заказа не меняются (ADR-0009).

```text
apps/integrations/poster/
  models.py      PosterConnection, PosterRef, PosterOrderPush, PosterWebhookEvent
  client.py      запросы к API Poster (httpx), разбор ошибок
  oauth.py       вход владельца, обмен кода на токен, выбор точки
  menu_sync.py   меню из Poster → MenuCategory, MenuItem, MenuItemVariant,
                 ModifierGroup, Modifier
  orders.py      заказ Botera → онлайн-заказ; статусы из Poster
  webhooks.py    приём вебхука: подпись, входящий журнал, задача
  tasks.py       задачи Celery
  admin.py       раздел «Poster» в Admin
```

### Данные

| Модель | Что хранит |
|---|---|
| `PosterConnection` | заведение, аккаунт и номер аккаунта Poster, точка (`spot_id`), токен (зашифрован), срок токена (2 года), статус, время и итог последней синхронизации, последняя ошибка, товар «Доставка». Уникально: заведение; пара «номер аккаунта + точка» |
| `PosterRef` | соответствие объекта Poster объекту Botera: заведение, вид (категория, позиция, вариант, группа добавок, добавка), id в Poster → id в Botera; уникально «заведение + вид + id в Poster»; отметка «удалён в Poster» |
| `PosterOrderPush` | передача заказа: один к одному с `Order`; состояние `pending → sending → sent / failed / unknown`, id онлайн-заказа и чека Poster, попытки, последняя ошибка |
| `PosterWebhookEvent` | входящий журнал вебхуков: ключ от дублей (номер аккаунта, сущность, id, действие, время), тело, итог обработки |

### 1. Подключение (OAuth)

- «Подключить Poster» в Admin открывает
  `https://joinposter.com/api/auth?application_id=…&redirect_uri=…&response_type=code`.
  Кто подключает — владелец заведения в Admin (`acts_for_partner` /
  `owns_partner`); заведение запоминается в сессии Django до ухода в Poster,
  а если Poster вернёт параметр `state` (шаг 0) — ещё и одноразовый ключ в
  нём.
- Poster возвращает на `/integrations/poster/oauth/callback/` с `code` и
  `account`; обмен кода на токен — `POST https://{account}.joinposter.com/api/v2/auth/access_token`
  (form-data). Без сессии с ключом — отказ: подключение начинается только из
  Admin Botera (установка из маркетплейса — позже).
- Точка: `spots.getSpots`; одна — сразу, несколько — выбор.
- Отключение: статус «отключено», токен стирается; меню и ссылки остаются.

### 2. Меню из Poster

Задача `sync_menu(connection)` читает Poster без открытой транзакции, затем
одной транзакцией под блокировкой строки `PosterConnection` записывает
изменения — две синхронизации одного заведения не пересекаются.

| Poster | Botera |
|---|---|
| категория (`menu.getCategories`), родитель | `MenuCategory`, `parent` |
| товар (тип 3) и тех. карта (тип 2) | `MenuItem`; цена — `spots[].price` своей точки (в копейках) |
| полуфабрикат (тип 1) | не переносится |
| вариант товара (`modifications`, `modificator_id`) | `MenuItemVariant` |
| набор модификаций тех. карты (`group_modifications`, `num_min` / `num_max`) | `ModifierGroup` этой позиции, `min_choices` / `max_choices` |
| модификация (`dish_modification_id`, `price`) | `Modifier` |
| скрыт (`hidden`, `spots[].visible = 0`), удалён | позиция «нет в наличии», ссылка помечена «удалён в Poster» |
| фото (`photo`, `photo_origin`) | `MenuItem.image_url`, если владелец не загрузил своё |

Владение полями: Poster — название, цена, категория, варианты, добавки,
видимость; Botera — переводы, описание, отметки, свои фото, способы заказа
(`available_*`), порядок внутри категории. Синхронизация не трогает поля
Botera; Admin не даёт править поля Poster у подключённого заведения.

Когда запускается: кнопка «Обновить меню» в Admin; вебхуки `product`, `dish`,
`category` (не сразу — одна синхронизация через ~60 секунд после последнего
изменения); раз в сутки ночью.

### 3. Заказ на кассу

- После коммита оформления (`apps/billing/remote_orders.py:place_remote_order`,
  там же, где сейчас уходит уведомление персоналу) создаётся
  `PosterOrderPush` в `pending` и ставится задача. Сервис оплаты про Poster
  не знает: связь — через сигнал после коммита, на который подписано
  приложение Poster.
- Задача захватывает строку короткой транзакцией (`pending → sending`), шлёт
  `incomingOrders.createIncomingOrder` без открытой транзакции, записывает
  итог своей транзакцией — как рассылки в ADR-0008.
- Что передаётся: `spot_id`; `phone`, `first_name`; `address` для доставки;
  строки — `product_id`, `modificator_id` для варианта, `modification`
  (`[{"m": id, "a": количество}]`) для добавок, `count`; стоимость доставки —
  строкой с товаром «Доставка»; `comment` — способ, время («как можно скорее»
  или «к 18:30»), комментарий гостя и метка `Botera #<код заказа>`. Без
  `payment`: в v1 предоплаты нет.
- Ошибки: временные (сеть, 5xx, таймаут, лимит) → `unknown`, перед повтором —
  поиск своего заказа по метке (`incomingOrders.getOwnIncomingOrders` с
  `date_from`); нашёлся — `sent`, нет — новая попытка; до 5 попыток с
  паузами. Окончательная ошибка (нет товара в Poster, неверный токен) →
  `failed` и сообщение персоналу заведения в Telegram («Заказ #… не дошёл
  до Poster — примите его вручную») — оно уходит, даже если уведомления о
  заказах в режиме Poster выключены.

### 4. Статус из Poster

- Вебхук `incoming_order` (`changed`) → задача читает онлайн-заказ и по
  `status` ведёт заказ Botera: 1 (принят) → «Принят», 7 (отменён) →
  «Отменён» с возвратом счёта, как у отмены неоплаченного заказа
  (`apps/billing/remote_orders.py:cancel_unpaid_remote_order`).
- Сейчас отмену и отметку оплаты делает только сотрудник
  (`apps/billing/remote_orders.py:record_payment_on_receipt` проверяет
  исполнителя). Для действий из Poster нужен системный исполнитель «Poster»:
  заведение берётся из подключения, в истории заказа — «из Poster».
- Закрытый чек (`transaction`) — PQ-059: «Завершён» сейчас достижим только
  через «Готов» (`apps/orders/services.py:ORDER_STATUS_TRANSITIONS`), а
  оплату в Botera никто не отметит. Решение владельца нужно до шага 6.

### Вебхуки

`POST /integrations/poster/webhook/` — без CSRF, сразу отвечает
`{"status": "accept"}`, обработка — в задаче Celery:

1. подпись: md5 от `account;object;object_id;action;[data;]time;секрет`,
   сравнение `hmac.compare_digest`; неверная — 403, ничего не пишется;
2. запись `PosterWebhookEvent`; дубль по ключу — ответ «accept» без новой
   задачи;
3. подключение по номеру аккаунта (для онлайн-заказа — ещё и по точке);
   нет активного подключения — событие отмечается «не наше».

Нужные вебхуки в настройках приложения Poster: `incoming_order`,
`transaction`, `product`, `dish`, `category`. Адреса OAuth и вебхуков в
настройках приложения должны совпадать с адресами сервера.

### Настройки

`POSTER_APPLICATION_ID`, `POSTER_APPLICATION_SECRET`, `POSTER_REDIRECT_URI` —
в `core/settings/env.py`, `.env.example`, `.env.production.example` и
`docs/engineering/DEPLOYMENT.md` на шаге 1. Значения вписывает владелец.

## Шаги

| Шаг | Что | Проверяет владелец |
|---|---|---|
| 0 | Проверка на пробном аккаунте Poster: разовый скрипт вне репозитория, личный токен — ответы на вопросы ниже | ответы и что меняется в плане |
| 1 | Основа: приложение, модели и миграции, `httpx`, клиент API с тестами на подменённых ответах, настройки окружения, раздел «Poster» в Admin только для чтения | модели и Admin |
| 2 | Подключение: OAuth из Admin, выбор точки, отключение | подключение пробного аккаунта |
| 3 | Меню из Poster по кнопке и ночью; владение полями; поля Poster только для чтения в Admin | меню пробного аккаунта в боте |
| 4 | Вебхуки: подпись, входящий журнал, обновление меню по изменениям | изменение цены в Poster видно в боте |
| 5 | Заказ на кассу: передача, повторы без дублей, сообщение о сбое | заказ из бота на кассе Poster |
| 6 | Статусы из Poster: принят, отклонён; закрытый чек — по PQ-059 | гость получает статус |
| 7 | Оформление в режиме Poster: только оплата при получении, без бонусов, товар «Доставка» | путь гостя |
| 8 | Пилот: весь путь на пробном аккаунте, документы; затем первое заведение — на своём домене и сервере | готовность к пилоту |

Оценка — 4–5 недель на шаги 0–8. До пилота нужен свой домен и сервер с
HTTPS: временный туннель показывает предупреждения браузера и не годится для
вебхуков и входа владельца.

## Проверить на шаге 0

1. Онлайн-заказ из API виден на кассе (iOS, Android, Windows): как выглядят
   комментарий, телефон, адрес и время; можно ли принять и отклонить.
2. Вебхук `incoming_order` приходит при принятии и отклонении; через сколько;
   как онлайн-заказ связан с чеком (`transaction_id`) и что приходит при
   закрытии чека.
3. Варианты товара (`modifications`, `modificator_id`) — в ответе есть, в
   таблице полей не описаны; цена модификации тех. карты — в копейках или в
   гривнах (описано «в деньгах», у товара — в копейках).
4. Формат ссылки на фото (`photo`, `photo_origin`) и открывается ли она без
   токена.
5. Принимает ли `/api/auth` параметр `state` и возвращает ли его (в
   документации нет).
6. Можно ли передать способ (самовывоз / доставка): в ответе есть `type`, в
   параметрах — нет.
7. Ограничения частоты запросов и ответ при превышении.
8. Как установка из маркетплейса передаёт аккаунт — чтобы потом связать её с
   заведением Botera.

## Тесты

Без сети: ответы Poster подменяются. Подпись вебхука (верная, неверная,
с `data`); повтор одного вебхука; передача заказа — успех, временная ошибка
и повтор без второго онлайн-заказа (поиск по метке), окончательная ошибка и
сообщение персоналу; меню — новые, изменённые, скрытые и удалённые позиции,
варианты и добавки, поля Botera не затираются; переходы статусов из Poster;
чужое заведение — вебхук другого аккаунта не трогает заказ. Захват строки
передачи и синхронизация меню под блокировкой — тест на PostgreSQL.
