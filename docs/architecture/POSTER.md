# Подключение к Poster (PQ-058) — план v1

**Статус:** в работе; решение владельца 2026-11-20 (ADR-0010). Шаг 0 —
проверка на пробном аккаунте — пройден 2026-11-20, итоги — в конце. Шаг 1 —
основа (записи, запросы к API, страницы Admin только для чтения) — сделан
2026-11-20. Шаг 2 — подключение из Admin, выбор точки, отключение — сделан
2026-11-20. Меню и заказы — шаги 3–6.
Работа идёт по шагам ниже, каждый шаг проверяет владелец. Работа не ждёт
интервью с заведениями (владелец 2026-11-20).

Заведение работает на кассе Poster и подключает к ней Botera Shop: меню
приходит из Poster, заказы из бота — на кассу онлайн-заказами, гость узнаёт в
Telegram, принят ли заказ. Решение и его причины — [ADR-0010](../decisions/ADR-0010.md).

## Решения владельца 2026-11-20

- Границы v1 — как ниже в «Что входит»: только оплата при получении, бонусы в
  режиме Poster — с v2.
- Новая зависимость `httpx` для запросов к Poster — согласована.
- Работа идёт независимо от интервью с заведениями.

## Что входит в v1

- Подключение в один клик из Admin Botera: вход в Poster, выбор точки.
- Меню из Poster: категории, позиции, цены точки, варианты, добавки,
  видимость; обновление по вебхукам и ночью.
- Заказы самовывоза и доставки из бота уходят на кассу Poster онлайн-заказом
  (телефон, имя, адрес, время, комментарий, метка `Botera #<код заказа>`).
- Принят или отклонён на кассе → гость получает обычное сообщение о статусе.

Не входит в v1: бонусы на чеки Poster, предоплата переводом, заказы стола и
счета стола, продажа на кассе Botera, отправка почтой, экран кухни Botera,
вызов персонала, виджет на кассе Poster, установка из маркетплейса Poster.

## Как это видит владелец заведения

1. Admin → «Настройки» → «Poster» → «Подключить Poster» → вход в свой
   аккаунт Poster и согласие → кнопка «Это точка «…»», если точек несколько
   (сделано, шаг 2).
2. Меню появляется в Botera; владелец добавляет фото, описания и переводы,
   отмечает способы заказа. Поля из Poster (название, цена, категория,
   варианты, добавки) в Admin только для чтения, с пометкой «из Poster».
3. Гость заказывает в боте как сейчас; на кассе появляется онлайн-заказ
   с пометкой «З собою» или доставкой с адресом и временем; кассир принимает
   его или отклоняет. Цена доставки из Botera приходит в чек сама.
4. «Отключить Poster» — заказы больше не передаются, меню остаётся как было,
   его снова можно править в Botera.

## Устройство

Приложение `apps/integrations/poster` (метка `poster`) — адаптер на краю,
как бот и Admin: вызывает сервисы заказа и меню и не повторяет их правила.
Ядро счёта (`apps/billing/services.py`) и модель заказа не меняются
(ADR-0009). Уже есть: `apps/integrations/poster/models.py`,
`apps/integrations/poster/client.py`, `apps/integrations/poster/admin.py`
(шаг 1), `apps/integrations/poster/services.py`,
`apps/integrations/poster/views.py` (шаг 2); остальное — по шагам.

```text
apps/integrations/poster/
  models.py      PosterConnection, PosterRef, PosterOrderPush, PosterWebhookEvent
  client.py      запросы к API Poster (httpx), разбор ошибок, обмен кода OAuth
  services.py    подключение: начало, возврат Poster, выбор точки, отключение
  views.py       возврат Poster после входа владельца
  menu_sync.py   меню из Poster → MenuCategory, MenuItem, MenuItemVariant,
                 ModifierGroup, Modifier
  orders.py      заказ Botera → онлайн-заказ; статусы из Poster
  webhooks.py    приём вебхука: подпись, входящий журнал, задача
  tasks.py       задачи Celery
  admin.py       раздел «Poster» в Admin
```

### Данные

| Модель | Что хранит |
|---|---|
| `PosterConnection` | заведение, логин и номер аккаунта Poster, точка (`spot_id`), статус («ждёт выбора точки», «работает», «отключено»), токен (шифром, `set_access_token` / `get_access_token`), срок токена (2 года), тариф Poster, кто подключил, когда обновлено меню, последняя ошибка. Уникально: заведение; среди работающих — пара «номер аккаунта + точка». Логин — только буквы, цифры и дефис: он становится адресом `https://<логин>.joinposter.com` |
| `PosterRef` | соответствие объекта Poster объекту Botera: заведение, вид (категория, позиция, вариант, группа добавок, добавка), id в Poster → id в Botera; уникально «заведение + вид + id в Poster»; отметка «удалён в Poster» |
| `PosterOrderPush` | передача заказа: один к одному с `Order`; состояние `pending → sending → sent / failed / unknown`, id онлайн-заказа и чека Poster, итог чека (сумма, оплачено), попытки, последняя ошибка |
| `PosterWebhookEvent` | входящий журнал вебхуков: ключ от дублей — хеш аккаунта, сущности, id, действия, времени и `data` (`PosterWebhookEvent.dedupe_key_for`; без `data` два события одного чека в одну секунду, как на шаге 0, слились бы в одно; подпись в ключ не входит), заведение (известно после проверки подписи), тело, итог обработки |

### 1. Подключение (OAuth) — сделано, шаг 2

Сервис — `apps/integrations/poster/services.py`, возврат Poster —
`apps/integrations/poster/views.py:oauth_callback`, кнопки —
`apps/integrations/poster/admin.py:PosterConnectionAdmin`.

- Кто: владелец заведения или его сети (`owns_partner`) или платформа —
  проверяется заново на каждом шаге. Менеджер с правами на профиль
  заведения видит страницу, но без кнопок. Страница «Poster» в «Настройках»
  видна и до подключения: на ней кнопка «Подключить Poster» (если платформа
  не вписала `POSTER_*` — надпись, что подключение не настроено).
- «Подключить Poster» — POST с токеном CSRF (`connect/` страницы Admin):
  `start_connection` запоминает в сессии Django заведение, человека и время и
  отправляет на `https://joinposter.com/api/auth?application_id=…&redirect_uri=…&response_type=code`.
  Параметр `state` Poster не возвращает (шаг 0), поэтому возврат
  принимается, только если в этой же сессии было нажатие: не старше 15 минут,
  того же человека, и тратится один раз (`take_started_connection`). Так чужой
  код входа нельзя подсунуть владельцу по ссылке. Платформа (без своего
  заведения) подключать не может — только из Admin заведения.
- Возврат на `/integrations/poster/oauth/callback/` с `code` и `account`
  (`error` — вход отменён): без входа в Admin — на вход; логин Poster
  проверяется до запроса; обмен кода — `POST https://{account}.joinposter.com/api/v2/auth/access_token`
  (form-data), затем `spots.getSpots` — оба запроса до транзакции. В ответе
  обмена, кроме токена, — номер аккаунта и тариф (наборы добавок у тех. карт
  есть только на тарифах Business и Pro). Отказ Poster — сообщение с его
  причиной, ничего не сохраняется.
- Сохранение — под блокировкой строки `PosterConnection` заведения (или
  новая строка): токен шифром, срок — два года, тариф, точки аккаунта
  (`available_spots`, удалённые точки Poster отброшены), кто подключил.
  Одна точка — сразу «работает»; несколько — «ждёт выбора точки» и кнопки
  «Это точка «…»» (`choose_spot`). Точка, уже работающая у другого
  заведения Botera, не забирается: проверка до сохранения и частичный
  уникальный индекс на гонку двух заведений (тест на PostgreSQL).
- Повторное подключение («Подключить заново») обновляет ту же запись: новый
  токен, точки, выбор точки заново.
- «Отключить Poster» (с подтверждением): статус «отключено», токен и его
  срок стираются; аккаунт, точка, меню и ссылки остаются.
- Установка из маркетплейса Poster (начинается в Poster, без нажатия в
  Admin) — позже, перед публикацией.

### 2. Меню из Poster

Задача `sync_menu(connection)` читает Poster без открытой транзакции, затем
одной транзакцией под блокировкой строки `PosterConnection` записывает
изменения — две синхронизации одного заведения не пересекаются.

| Poster | Botera |
|---|---|
| категория (`menu.getCategories`), родитель | `MenuCategory`, `parent` |
| товар (тип 3) и тех. карта (тип 2) | `MenuItem`; цена — `price` своей точки, **в копейках** |
| полуфабрикат (тип 1) | не переносится |
| вариант товара (`modifications`: `modificator_id`, `spots[].price` — **в копейках**); у товара с вариантами `price` пустой | `MenuItemVariant` |
| набор модификаций тех. карты (`group_modifications`: `num_min` / `num_max`; «одно из» — 1 / 1, обязателен) | `ModifierGroup` этой позиции, `min_choices` / `max_choices` |
| модификация (`dish_modification_id`, `price` — **в гривнах**) | `Modifier` |
| скрыт (`hidden`, `spots[].visible = 0`), удалён | позиция «нет в наличии», ссылка помечена «удалён в Poster» |
| фото (`photo`, `photo_origin` — путь) | `MenuItem.image_url` = `https://joinposter.com` + путь (открывается без токена), если владелец не загрузил своё |

Всё меню с вариантами и наборами добавок приходит одним
`menu.getProducts` — по одному запросу на позицию не нужно.

Владение полями: Poster — название, цена, категория, варианты, добавки,
видимость; Botera — переводы, описание, отметки, свои фото, способы заказа
(`available_*`), порядок внутри категории. Синхронизация не трогает поля
Botera; Admin не даёт править поля Poster у подключённого заведения.

Когда запускается: кнопка «Обновить меню» в Admin; вебхуки `product`, `dish`,
`category` (не сразу — одна синхронизация через ~60 секунд после последнего
изменения); раз в сутки ночью.

### 3. Заказ на кассу

- После коммита оформления (`apps/billing/remote_orders.py:place_remote_order`,
  там же, где сейчас уходит уведомление персоналу) создаётся
  `PosterOrderPush` в `pending` и ставится задача. Сервис оплаты про Poster
  не знает: связь — через сигнал после коммита, на который подписано
  приложение Poster.
- Задача захватывает строку короткой транзакцией (`pending → sending`), шлёт
  `incomingOrders.createIncomingOrder` без открытой транзакции, записывает
  итог своей транзакцией — как рассылки в ADR-0008.
- Что передаётся: `spot_id`; `phone`, `first_name`; `service_mode` — 2
  самовывоз («З собою»), 3 доставка; для доставки — `address` и
  `delivery_price` (в копейках, Poster сам прибавляет её к чеку); время «к
  18:30» — `delivery_time` (`Y-m-d H:i:s`, местное время заведения); строки —
  `product_id`, `modificator_id` для варианта, `modification`
  (`[{"m": id, "a": количество}]`) для добавок, `count`; `comment` —
  комментарий гостя и метка `Botera #<код заказа>`. Без `payment`: в v1
  предоплаты нет. Поля `service_mode`, `delivery_price`, `delivery_time` в
  документации 2023 года нет — проверены на шаге 0.
- Ошибки: временные (сеть, 5xx, таймаут) → `unknown`, перед повтором — поиск
  своего заказа по метке: `incomingOrders.getOwnIncomingOrders` приложению не
  доступен («нет прав», шаг 0), поэтому ищем среди вебхуков `incoming_order`
  `added` этой точки после отправки и читаем их `incomingOrders.getIncomingOrder`
  (или списком `incomingOrders.getIncomingOrders` — проверить на шаге 5);
  нашёлся — `sent`, нет — новая попытка; до 5 попыток с паузами.
  Окончательная ошибка (нет товара в Poster, неверный телефон — код 155,
  не выбрана обязательная добавка — код 210, неверный токен) →
  `failed` и сообщение персоналу заведения в Telegram («Заказ #… не дошёл
  до Poster — примите его вручную») — оно уходит, даже если уведомления о
  заказах в режиме Poster выключены.

### 4. Статус из Poster

- Вебхук `incoming_order` (`changed`) → задача читает онлайн-заказ и по
  `status` ведёт заказ Botera: 1 (принят) → «Принят», 7 (отменён) →
  «Отменён» с возвратом счёта, как у отмены неоплаченного заказа
  (`apps/billing/remote_orders.py:cancel_unpaid_remote_order`).
- Чек онлайн-заказа Poster создаёт сразу (`transaction_id` есть в ответе на
  создание). После закрытия или удаления чека онлайн-заказ остаётся в
  статусе 1 — исход берётся из чека: `status` 2 — закрыт, 3 — удалён, 4 —
  чек отклонённого онлайн-заказа (4 в документации нет).
- Закрытый чек (вебхук `transaction`, затем `dash.getTransaction`) — PQ-059,
  решено 2026-11-20:

  | Чек Poster | Что делает Botera |
  |---|---|
  | закрыт (`status` 2) с оплатой: `pay_type` 1 — наличные, 2 — карта, 3 — смешанная | остаток счёта — оплата «Наличные» / «Карта (терминал)» / «Смешанная» без сотрудника, источник «poster», номер чека; заказ «Завершён» из любого незакрытого статуса, как по «Получил(а)» (PQ-029) |
  | закрыт, а заказ гость уже отметил «Получил(а)» | только оплата |
  | закрыт без оплаты (`pay_type` 0, причина в `reason`: «Гість пішов», «За рахунок закладу», «Помилка офіціанта») или удалён (`status` 3, вебхук `transaction` `removed`); заказ в Botera уже отменён | ничего автоматически: сообщение персоналу заведения и пометка в Admin, решает сотрудник |
  | кассир изменил строки (вебхук `transaction` `changed`, `changeitemcount`); очищенный чек остаётся открытым на 0 ₴ | ничего, пока чек не закрыт или не удалён; при закрытии расхождение суммы видно в Admin |

  Сумма оплаты — по счёту Botera, не по чеку: в чеке могут быть покупки сверх
  заказа из бота. Итог чека (`sum`, `payed_sum`) хранится в
  `PosterOrderPush`; если он отличается от счёта, это видно в Admin — деньги
  в Botera тихо не правятся. Кешбэк за такую оплату в v1 не начисляется.
- Сейчас отмену и отметку оплаты делает только сотрудник
  (`apps/billing/remote_orders.py:record_payment_on_receipt` проверяет
  исполнителя), а «Завершён» достижим только через «Готов»
  (`apps/orders/services.py:ORDER_STATUS_TRANSITIONS`). Для действий из
  Poster нужен системный исполнитель «Poster» и свой переход, как
  `apps/orders/services.py:GUEST_RECEIPT_CONFIRMABLE_STATUSES`: заведение
  берётся из подключения, в истории заказа — «из Poster».

### Вебхуки

`POST /integrations/poster/webhook/` — без CSRF, сразу отвечает
`{"status": "accept"}`, обработка — в задаче Celery:

1. подпись: md5 от `account;object;object_id;action;[data;]time;секрет`,
   сравнение `hmac.compare_digest`; неверная — 403, ничего не пишется;
2. запись `PosterWebhookEvent`; дубль по ключу — ответ «accept» без новой
   задачи;
3. подключение по номеру аккаунта (для онлайн-заказа — ещё и по точке);
   нет активного подключения — событие отмечается «не наше».

Подпись считается от поля `data` в том виде, как оно пришло (это строка
JSON), до разбора. Poster шлёт вебхуки парами — по онлайн-заказу и по чеку —
через 1–2 секунды после события; действия: `added`, `changed`, `closed`,
`removed`.

Нужные вебхуки в настройках приложения Poster: `incoming_order`,
`transaction`, `product`, `dish`, `category` (уже выбраны вместе с `client`).
Адреса OAuth и вебхуков в настройках приложения должны совпадать с адресами
сервера.

### Настройки

`POSTER_APPLICATION_ID`, `POSTER_APPLICATION_SECRET`, `POSTER_REDIRECT_URI` —
из окружения (`core/settings/env.py`, `.env.example`,
`.env.production.example`, `docs/engineering/DEPLOYMENT.md`, шаг 1).
Значения вписывает владелец.

Запросы (`apps/integrations/poster/client.py`): `PosterClient.call` —
`GET` или `POST` с JSON на `https://joinposter.com/api/<метод>`, токен в
строке запроса; `exchange_code` — обмен кода OAuth на токен на адресе
аккаунта, логин проверяется до запроса. Любая неудача — `PosterError` с кодом
Poster, HTTP-статусом и признаком «временная» (сеть, таймаут, 5xx, 429 —
повторить позже; остальное — Poster отказал). Ошибки не несут токен, секрет и
код OAuth, без цепочки исключений с адресом запроса. `httpx` пишет адрес
запроса (с токеном) в журнал на INFO — журналы `httpx` и `httpcore` подняты до
WARNING (`core/logging/config.py`, повтор — при импорте клиента).

## Шаги

| Шаг | Что | Проверяет владелец |
|---|---|---|
| 0 | Проверка на пробном аккаунте Poster: разовый скрипт вне репозитория — **пройден 2026-11-20**, итоги ниже | итоги и что меняется в плане |
| 1 | Основа: приложение, модели и миграции, `httpx`, клиент API с тестами на подменённых ответах, настройки окружения, раздел «Poster» в Admin только для чтения — **сделан 2026-11-20** | модели и Admin |
| 2 | Подключение: OAuth из Admin, выбор точки, отключение — **сделан 2026-11-20** | подключение пробного аккаунта |
| 3 | Меню из Poster по кнопке и ночью; владение полями; поля Poster только для чтения в Admin | меню пробного аккаунта в боте |
| 4 | Вебхуки: подпись, входящий журнал, обновление меню по изменениям | изменение цены в Poster видно в боте |
| 5 | Заказ на кассу: передача, повторы без дублей, сообщение о сбое | заказ из бота на кассе Poster |
| 6 | Статусы из Poster: принят, отклонён; закрытый чек — оплата по счёту и «Завершён» (PQ-059) | гость получает статус, оплата видна в Admin |
| 7 | Оформление в режиме Poster: только оплата при получении, без бонусов, цена и время доставки — полями Poster | путь гостя |
| 8 | Пилот: весь путь на пробном аккаунте, документы; затем первое заведение — на своём домене и сервере | готовность к пилоту |

Оценка — 4–5 недель на шаги 0–8. Для разработки хватает временного туннеля
(шаг 0 прошёл через него: вход приложения и вебхуки работают). До пилота
нужен свой домен и сервер с HTTPS: туннель живёт, пока открыт ноутбук, а

## Тесты

Без сети: ответы Poster подменяются. Подпись вебхука (верная, неверная,
с `data`); повтор одного вебхука; передача заказа — успех, временная ошибка
и повтор без второго онлайн-заказа (поиск по метке), окончательная ошибка и
сообщение персоналу; меню — новые, изменённые, скрытые и удалённые позиции,
варианты и добавки (цены вариантов в копейках, добавок — в гривнах,
обязательная группа «одно из»), поля Botera не затираются; доставка —
`service_mode`, `delivery_price`, `delivery_time`; ошибки 155 и 210 —
окончательные; переходы статусов из Poster; закрытый чек — оплата остатка один раз (повтор вебхука не добавляет вторую), способ по `pay_type`, без кешбэка, расхождение суммы помечено, закрытие без оплаты и удаление — только сообщение;
чужое заведение — вебхук другого аккаунта не трогает заказ. Захват строки
передачи и синхронизация меню под блокировкой — тест на PostgreSQL.
